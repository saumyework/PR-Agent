This PR is open. It adds Portfolio and Program master data for PMO: services, validators, DTOs and locale keys. It also adds structure-link validation (OOTB-15818) to Create and Update Project, and a cascade that rewrites project PortfolioId when a program is re-parented.

Nothing is a definite blocker, but several points should be fixed before merge. Code uniqueness is case-sensitive and has no DB unique index. The program-to-project cascade is a bulk write that may not be atomic and records no audit trail. The new Update Project validator can block unrelated edits on stale links. There are no tests, and the description is empty.

The team must decide whether a master-data edit should silently rewrite projects. It must also decide whether to split OOTB-15818 and the Brain/doc files out of this PR, and when the unique-index migration will land.

Method: 4 independent review calls over 1 shard(s), evidence machine-checked (2 unverifiable candidates discarded), then one merge call.

Suggestions

F1 src/Modules/Project/Project.Application/Services/ProgramService.cs:107

Program re-parent cascade: atomicity, unbounded load. ProgramService.UpdateAsync saves the program, then SyncProjectPortfolioAsync loads every non-deleted project as tracked entities and rewrites PortfolioId. If the repository UpdateAsync methods save immediately, or use different contexts, a mid-way failure leaves the program and its projects inconsistent. The change also skips project audit fields and the activity log. Wrap the steps in one transaction, use ExecuteUpdateAsync or an id projection, and confirm this side effect as a team decision. Also at: src/Modules/Project/Project.Application/Services/ProgramService.cs:115.

F2 src/Modules/Project/Project.Application/UseCases/Projects/Commands/UpdateProject/UpdateProjectCommand.cs:24

Update validator blocks unrelated project edits. Because the Update validator enforces program.PortfolioId == project.PortfolioId on every project save, a project can no longer be saved if its linked program or portfolio was later soft-deleted or moved. The same applies to any other caller of PUT projects, such as dynamic-pmo. The cascade in ProgramService only covers one direction. Consider validating only when the ids changed compared with the stored project, so unrelated edits are not blocked.

F3 src/Modules/Project/Project.Application/Services/PortfolioService.cs:120

Code uniqueness case-sensitive, no unique index. The Portfolio and Program code checks compare exactly, so 'PFL-1' and 'pfl-1' can coexist, while the title check is trim and case-insensitive. Both are check-then-insert with no DB unique index, so concurrent creates can produce duplicates. Normalize the code comparison and add a filtered unique index, with its migration. Also at: src/Modules/Project/Project.Application/UseCases/Portfolios/Commands/CreatePortfolio/CreatePortfolioCommandValidator.cs:28, src/Modules/Project/Project.Application/Services/PortfolioService.cs:121.

F4 src/Modules/Project/Project.Application/Services/PortfolioService.cs:97

Description has no length limit. Code and Title have MaximumLength rules, but Description is accepted unbounded in the Portfolio and Program Create/Update validators. A very large payload would be stored as-is. Add a MaximumLength rule or confirm the column is intentionally unbounded.

F5

PR scope, description and tests. The title names OOTB-15763 and OOTB-15766, but the diff also carries OOTB-15818 and OOTB-15761 changes plus Brain and daily-note files. The description is empty and no tests are added for the uniqueness rules, the cascade or ProjectStructureRules. Several dependencies sit outside the PR: Toolbox document types, menu rows, the unique-index migration and the unconfirmed TableType ids 417/418. Split or describe the scope, fill in the description, remove the review chatter from the Brain files, and add tests or a manual test plan.
