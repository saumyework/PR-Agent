Large backend sync (~3,800 additions across ~100 files) merging three features into version/0.11.0: a new RMS Resource Schedule subsystem (booking/eligibility engine wired into EMS venue booking), SDM SLA Escalation Field/Notification CRUD modules, and a multipart-form rework of the SDM Request create endpoint (file attachments). The new resource-scheduling engine itself is well structured (Service/Evaluator/Handlers/Validators cleanly separated, transactional sync, new integration tests). However, review turned up a validation regression on SLA Policy escalation levels, a client-controlled field that can bypass a delete guard on SDM Requests, a shared lookup service whose filtering semantics silently changed, and an integration test that posts to a route the endpoint doesn't expose — any of which would ship a real defect if merged as-is.

Errors Warnings Notes Passed

Must-Fix

src/Modules/Sdm/Sdm.Application/UseCases/SlaPolicies/Commands/Create/CreateCommand.cs:32

Validation regression on SLA escalation levels. Both CreateValidator and UpdateCommand.cs's UpdateValidator (same pattern) drop the previously-existing RuleForEach(...).ChildRules(...) block that required Recipients to be non-empty when IsEnable is true, and required Level > 0. Nothing replaces these checks — only the uniqueness rule was kept (and rescoped to be per-TriggerType instead of global, which looks intentional). As written, an SLA policy can now be saved with an enabled escalation level that has zero recipients, or with Level <= 0, silently breaking escalation processing downstream.

src/Modules/Sdm/Sdm.Application/Services/RequestService.cs (MapRequestUpdates)

Update path bypasses the new delete guard. DeleteAsync now correctly blocks deletion unless the request's workflow is still in TransactionCategory.Start (draft) — but MapRequestUpdates, called from the plain UpdateAsync path, does requestDetails.Status = request.Status;, copying the client-supplied Status (the same soft-delete-style enum used elsewhere in this codebase, e.g. Status.Removed) straight onto the tracked entity with no workflow check at all. A client can achieve the same "removed" end-state through PUT that DELETE now explicitly disallows, defeating the guard just added a few lines away in the same file.

src/Modules/EnterpriseDataManagement/EnterpriseDataManagement.Application/Services/RdmLookupValueService.cs:23

Lookup filter semantics silently changed for all callers. The predicate changed from x.ParentId == parentId to (!parentId.HasValue || x.ParentId == parentId) in both branches. Previously, calling with parentId: null returned only true root items (ParentId == null); now it returns every item at that level regardless of parent. This is a shared, generic lookup service (used for cascading dropdowns across modules) — any existing caller that relied on "no parent = root only" semantics will now get an unfiltered result set instead. If this relaxation was intentional for one specific new caller, it should be scoped to that caller rather than changing behavior for every consumer of this method.

src/Web.API.Tests.Integration/Rms/ResourceSchedules/ResourceScheduleApiTest.cs:82

Integration test posts to a route that doesn't exist. RecordBookingAsync calls POST resource-schedules/record, but ResourceScheduleEndpoints.cs maps the create action at group.MapPost("/", ...) — i.e. POST resource-schedules/, with no /record segment anywhere in the file. Every test built on this helper (RecordResourceBookingTests, CancelResourceBookingTests, SyncResourceBookingsTests) depends on this call succeeding first, so all of them would 404 as written. Either the route or the test helper is wrong; this contradicts the PR checklist's "tested my changes locally" / "added unit tests" boxes.

Suggestions

src/Modules/Ems/Ems.Application/Services/EmsResourceSchedulePublisher.cs:23

Booking sync failures are silently swallowed. TryRecordBookingAsync/TryCancelBookingAsync/TrySyncBookingsAsync each catch Exception and only LogWarning. Since EventVenueService already runs an eligibility pre-check (EnsureInternalVenueScheduleEligibleAsync) before saving the venue, a later failure in the actual RMS write (e.g. a race with another booking created between the check and the write) leaves the EMS venue saved as booked with no corresponding RMS resource-schedule row, no user-facing error, and no retry — the two systems silently drift out of sync.

src/Modules/Rms/Rms.Contracts/ResourceSchedule/CancelResourceBookingCommand.cs, SyncResourceBookingsCommand.cs

Missing validators, inconsistent with sibling commands. RecordResourceBookingCommandValidator and UpdateResourceBookingCommandValidator both validate Source.IsInEnum(), but CancelResourceBookingCommand and SyncResourceBookingsCommand have no validator at all despite also taking a Source enum and (for sync) a SourceReferenceKey Guid. Per the team's always-enforced validation check, every write-path command should get the same coverage as its siblings.

src/Modules/Rms/Rms.Application/Services/ResourceScheduleStatusEvaluator.cs + ResourceScheduleService.cs

Conflict check and booking write aren't atomic. EvaluateAsync reads current schedules to decide eligibility, then a separate call later writes the booking (RecordBookingAsync/UpsertBookingAsync) with no shared lock or transaction spanning both steps. Two concurrent requests for overlapping windows on the same resource could both pass the eligibility check and then both write, resulting in a double-booking that the feature is specifically meant to prevent.

src/Modules/Rms/Rms.Application/Services/ResourceScheduleService.cs:30

Test coverage gap on the write endpoints. New integration tests cover Record/Cancel/Sync, but there's no test for UpdateResourceBookingCommand, DeleteResourceBookingCommand, or evaluate-status — all newly-added write/decision endpoints with no regression coverage.

Notes

src/Modules/Ems/Ems.Application/Services/EmsResourceSchedulePublisher.cs:70

Stairstep LINQ indentation. The bookings pipeline in TrySyncBookingsAsync (.Where().Select().Where().Cast().ToList()) indents one level deeper per call instead of aligning the chain, inconsistent with the codebase's formatting convention for chained calls.

src/Modules/Ems/Ems.Application/Constants/EventVenueScheduleValidationMessageKeys.cs and src/Modules/Rms/Rms.Application/Constants/EventVenueScheduleValidationMessageKeys.cs

Duplicated constants class. The exact same six message-key constants are defined identically in both the Ems and Rms modules. Worth hoisting into a shared location (e.g. BuildingBlocks) so the two copies can't drift apart on a future change.

What's Good

Clean new subsystem structure. The RMS Resource Schedule feature (Service / Evaluator / Handlers / Validators / Contracts) follows the existing CQRS layering cleanly and reads as a coherent, well-separated addition.

Transactional multi-row sync. ResourceScheduleService.SyncBookingsAsync wraps the stale-cancel + upsert loop in an explicit DB transaction with rollback on failure — a correct choice for a multi-row operation that must stay consistent.

Early, user-facing conflict feedback. EventVenueService.EnsureInternalVenueScheduleEligibleAsync pre-checks resource availability before saving an EMS venue and surfaces a locale-keyed message on conflict, instead of failing silently or late.

Dependent-record checks extended correctly. DepartmentService.IsUsedAsync and ServiceUnitService.IsUsedAsync were both correctly extended to also check the new Request/SlaPolicy references before allowing deletion, preventing orphaned data.

Stale doc-region cleanup. The mislabeled #region Rms around SDM locale constants in Constants.cs was corrected to #region Sdm in passing.
