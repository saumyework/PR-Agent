Adds a new Request / RequestAttachment entity pair to the SDM module, along with EF Core configurations and dual-provider (PostgreSQL + SQL Server) migrations. The domain model wires up lookup relationships (type, status, mode, level, impact, urgency, priority, category, subcategory), a department, requester/technician users, and attachments, following the module's existing schema-isolation conventions (IgnoreSharedEntities). The main issue is that the hand/tool-generated migration files don't actually create the foreign-key constraints that the model configuration declares for most of the lookup relationships, which will cause model/database drift.

Must-Fix

src/Modules/Sdm/Sdm.Infrastructure/Migrations/PostgreSQL/Sdm/20260701123946_AddEventRequest.cs:1829-1958 (and the equivalent SqlServer migration at 20260701124004_AddEventRequest.cs:1934-4063)

The Requests table's CreateTable call only registers one foreign key (FK_Requests_Departments_DepartmentId), yet RequestConfiguration.cs (and the migration's own Designer.cs snapshot) declares HasOne(...).HasForeignKey(...) relationships with OnDelete(DeleteBehavior.NoAction) for RequestTypeId, RequestStatusId, ModeId, LevelId, ImpactId, UrgencyId, PriorityId, CategoryId, and SubcategoryId — all pointing at RdmLookupValue, which lives in the same Sdm schema and is not excluded by IgnoreSharedEntities (unlike User/Requester/Technician, which are correctly cross-schema and correctly have no FK). CreateIndex calls exist for all nine columns, but the matching table.ForeignKey(...) entries are missing. Applying this migration produces a database schema with no referential integrity for those nine relationships even though the C# model says they exist, and the next dotnet ef migrations add run is likely to generate a large, unexpected "fix" migration to reconcile the drift once someone else touches this DbContext. Regenerate the migration (e.g. re-run dotnet ef migrations add against the current model, or hand-add the missing table.ForeignKey calls for these 9 columns) so the migration matches the model it was scaffolded from.

Suggestions

src/Modules/Sdm/Sdm.Domain/Models/Request.cs:35

[Required] public Guid? PriorityId { get; set; } is the only required FK property declared as a nullable Guid?; every other required FK on this entity (RequestTypeId, RequestStatusId, ImpactId, UrgencyId, CategoryId, RequesterId) is a plain non-nullable Guid. The migration confirms the column is actually NOT NULL at the DB level, so the nullable CLR type is misleading to callers of the domain model (it suggests null is a legal transient state). Change it to Guid for consistency with the sibling FK properties.

src/Modules/Sdm/Sdm.Infrastructure/Data/Configurations/RequestConfiguration.cs:235-248

RequesterId and TechnicianId get no database index, unlike CategoryId/ImpactId/ModeId/etc., because their target (Shared.Domain.Models.User) is a cross-schema entity that IgnoreSharedEntities suppresses at design time — so EF never scaffolds an index for them. That suppression is correct for the FK, but these two columns are very likely to be filtered on in real usage ("my open requests", "requests assigned to me"). Consider adding explicit indexes via builder.HasIndex(e => e.RequesterId) / builder.HasIndex(e => e.TechnicianId) in RequestConfiguration.cs so lookups on these columns aren't full table scans as the table grows.
