Introduces SDM user-type-based access control: a new ISdmUserContext/ISdmRequestAuthorizationPolicy pair enforces that "SDMRequester" users can only view/create their own Request records (with technician-controlled fields locked and status forced to Open), and can never update or delete existing requests. Two new IEndpointFilters (DenySdmRequesters, DenySdmRequesterMutations) are wired onto 8 of the 9 SDM endpoint groups — full denial for admin/config endpoints (Hierarchy, OrganizationRole, PriorityMatrix, ServiceUnit, SlaEscalationField/Notification, SlaPolicy), mutation-only denial for Department (since a Requester still needs to read departments to submit a request, matching Request.DepartmentId). The Request endpoints themselves rely on the new service-layer policy rather than a filter, which is appropriate since they need per-record ownership checks, not blanket denial.

The core authorization logic is sound and consistently placed before any side-effecting work (DB writes, workflow calls) in Create/Update/Delete/GetById. No confirmed security holes were found. The main gaps are around code reuse (the new SdmUserContext.UserId duplicates the existing BaseService.UserId claim-parsing logic that RequestService already inherits), an i18n regression (new Forbidden/Validation messages are hardcoded English constants instead of going through the IStringLocalizer pattern every other exception in RequestService.cs uses), and no test coverage for the new authorization classes despite them being security-critical.

Suggestions

src/Modules/Sdm/Sdm.Application/Authorization/SdmUserContext.cs:20

Duplicates BaseService.UserId instead of reusing it. SdmUserContext.UserId re-implements the exact same claims lookup and even the same exception message ("UserId cannot be empty.") as BaseService.UserId (Shared.Infrastructure.Services.BaseService), which RequestService — the very class this PR modifies — already inherits and uses elsewhere in the same file (e.g. request.CreatedBy = UserId). Two copies of the same claim-parsing logic now need to be kept in sync if the claim type or fallback behavior ever changes. Consider having SdmUserContext take a dependency that reuses BaseService's logic, or exposing it as a shared helper, rather than copy-pasting it.

src/Modules/Sdm/Sdm.Application/Authorization/SdmAuthorizationMessages.cs:11

New Forbidden/Validation messages bypass localization. Every other user-facing exception message in RequestService.cs goes through IStringLocalizer<Localizer> with a Locale.* key (e.g. throw new NotFoundException(string.Format(localizer[Locale.RequestNotFound]))), but the new SdmAuthorizationMessages constants used by SdmRequestAuthorizationPolicy and the two endpoint filters are hardcoded English strings thrown directly. Since the app explicitly supports English/Arabic localization, Arabic-locale SDM requesters hitting a Forbidden/validation error from this new code path will see untranslated English text where sibling error paths are translated.

src/Modules/Sdm/Sdm.Application/Authorization/

No test coverage for new authorization logic. SdmRequestAuthorizationPolicy, SdmUserContext, and the two new IEndpointFilters are new, security-critical access-control code (who can view/create/update/delete SDM requests, and which admin endpoints a requester can reach), but the PR adds no unit tests for any of them. Worth at least covering the ownership/mutation-denial branches in SdmRequestAuthorizationPolicy, since a regression there directly changes who can see or modify whose data.

Unused constant added. SdmUserTypes.Technician = "SDMTechnician" is added but not referenced anywhere in this PR or the rest of the module — only SdmUserTypes.Requester is actually used (in SdmUserContext.IsRequesterAsync). If it's for a follow-up PR, fine to keep, but as it stands it's dead code.

src/Modules/Sdm/Sdm.Application/Authorization/SdmRequestAuthorizationPolicy.cs:30

Unreachable null-default branch. EnsureCanMutateExistingAsync(Request? existingRequest = null, ...) defaults its parameter to null, but both call sites (DeleteAsync, UpdateAsync) always pass a fetched Request. The null path (skip the ownership check, jump straight to the generic "mutation denied" message) is never exercised, which makes the method's contract less clear than it needs to be — either drop the default and require an existing request, or add a caller that actually needs the null case.

src/Modules/Sdm/Sdm.Application/Endpoints/RequestEndPoints.cs:87

Two read endpoints skip the new ownership checks. GET /sdmRequests/code/{code} (GetCodeExistsQuery) and GET /sdmRequests/ifUsed/{id} (CheckIfUsedQuery) call IRequestService.IsCodeExistsAsync/IsUsedAsync directly rather than going through GetAsync/GetByIdAsync, so they aren't scoped to the requester's own records. Impact is low (both return a bare boolean, no data disclosure), but a Requester can use ifUsed/{id} as an existence oracle for request IDs they don't own. Low priority given what little it leaks, but worth a conscious call on whether that's acceptable.

Good consolidation of duplicated logic. The inline requester-type lookup previously duplicated in RequestService.GetAsync is now centralized in ISdmUserContext.IsRequesterAsync(), with per-scope caching (_userTypeLoaded/_userType) so the endpoint filter and the service layer share one DB round-trip per request instead of each querying independently.

src/Modules/Sdm/Sdm.Application/Endpoints/

Admin/config endpoints (Hierarchy, OrganizationRole, PriorityMatrix, ServiceUnit, SlaEscalation*, SlaPolicy) get blanket DenySdmRequesters(), while Department only denies mutations — correctly reflecting that a Requester still needs to read departments to populate Request.DepartmentId on their own submissions. The Request aggregate itself is handled with fine-grained per-record ownership checks in the service layer instead of a filter, which is the right call since "can view/edit this record" isn't a route-level decision.

src/Modules/Sdm/Sdm.Application/Services/RequestService.cs:78

In CreateAsync/UpdateAsync/DeleteAsync/GetByIdAsync, the new policy checks are the first thing that happens after fetching/validating existence, ahead of workflow calls, normalization, or persistence — so unauthorized attempts fail fast without partial state changes or wasted work.
