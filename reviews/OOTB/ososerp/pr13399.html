This PR introduces cross-module (EMS ↔ RMS) resource-schedule conflict evaluation: a new ResourceScheduleStatusEvaluator in RMS that checks whether an internal venue/resource is booking-eligible for a set of time windows, exposed via a new evaluate-status query and wired into both EventVenueService (create/update guard) and EventVenueConflictHandler (workflow conflict check). It also adds two new read endpoints (resources-master/all, resource-schedules/calendar) and refactors ResourceScheduleService.GetAsync into a shared GetPagedAsync helper.

The architecture is sound (CQRS, FluentValidation, a clean evaluator service), but the new eligibility logic itself has two correctness bugs that directly undermine the double-booking prevention this PR exists to add: the venue time window is converted to UTC with a hardcoded zero offset instead of the event's actual timezone (unlike the sibling TimeZoneUtilities/ConflictManagementService pattern already in the codebase), and the schedule-exclusion filter uses OR instead of AND between the event-level key and the venue-level id, which can let a genuine double-booking of the same resource within the same event slip past undetected. There's also a file-upload-before-validation ordering bug that can orphan uploaded documents, and an unbounded schedule query on a path that's called on every venue create/update.

Errors Warnings Notes Passed

Must-Fix

src/Modules/Ems/Ems.Application/Utilities/EventVenueScheduleEvaluationMapper.cs:14-19

Venue time converted with a hardcoded zero UTC offset. ToDateTimeOffset builds the request windows as new(date.ToDateTime(time), TimeSpan.Zero), i.e. it treats the venue's local wall-clock Date/FromTime/ToTime as if they were already UTC. The sibling file in the very same folder, TimeZoneUtilities.ConvertToUtc, exists specifically to convert venue date/time using the event's actual timezone offset, and ConflictManagementService.ValidateConflictsForEventRequestVenuesAsync already threads eventSchedule.TimeZone through for exactly this purpose — confirming venue times are stored in local/event timezone, not UTC. Because this mapper ignores that offset, schedule conflict evaluation will compare the wrong UTC instants for any event whose timezone isn't UTC+00:00, producing false negatives (missed double-bookings) or false positives (blocking valid bookings) depending on the offset direction.

src/Modules/Rms/Rms.Application/Services/ResourceScheduleStatusEvaluator.cs:490-508

Schedule-exclusion filter uses OR instead of AND, over-excluding conflicts. IsExcluded treats a schedule as excluded from the conflict check if ExcludeSourceReferenceKey matches or ExcludeSourceReferenceId matches (after the ExcludeSource check). EventVenueScheduleEvaluationMapper.ToEvaluateRequest always passes ExcludeSourceReferenceKey = venue.EventRequestId (the event-level grouping key, also used by SyncResourceBookingsCommand to batch-replace all bookings sharing that key) and ExcludeSourceReferenceId = venue.Id (the specific venue/booking). With OR, evaluating one venue's eligibility will also exclude any other schedule belonging to the same event, not just this venue's own entry — so if the same physical resource is booked twice within the same event request (two different venues/time slots), the second booking's conflict check silently ignores the first one's existing schedule and lets the double-booking through. This should require both identifiers to match the same schedule row (or match on SourceReferenceId alone), not either one.

src/Modules/Ems/Ems.Application/Services/EventVenueService.cs:118-152

File uploaded before schedule-eligibility check, orphaning it on rejection. In this CreateAsync overload, eventDocumentService.CreateAsync(...) uploads the layout document earlier in the method, and only afterwards does the newly-added EnsureInternalVenueScheduleEligibleAsync run before repository.AddAsync. If the resource turns out to be schedule-ineligible, the method throws after the file has already been persisted, with no compensating delete — leaving an orphaned document on every rejected create-with-file. Contrast with the sibling UpdateAsync(eventVenue, file, companyCode, cancellationToken) overload a few lines down, which correctly runs EnsureInternalVenueScheduleEligibleAsync before the file-upload block. Move the eligibility check above the upload in this overload too.

src/Modules/Rms/Rms.Application/Services/ResourceScheduleStatusEvaluator.cs:451-453

Unbounded schedule query on a per-venue hot path. EvaluateAsync loads every Active schedule row for the resource (scheduleRepository.GetListAsync(rs => rs.ResourceMasterId == ... && rs.Status == Status.Active, ...)) with no date-range filter, then filters for window overlap in memory. This method is invoked on every internal-venue create/update (via EventVenueService) and once per venue in every workflow conflict check (via EventVenueConflictHandler's loop), so it runs frequently, and the schedule table only grows over time (old and future bookings alike stay Active until resolved/cancelled). The sibling ResourceScheduleService.GetPagedAsync already filters FromDateTime >= DateTimeOffset.UtcNow for a similar concern — this evaluator should filter schedules by the request's window range (e.g. FromDateTime < maxWindowEnd && (ToDateTime == null || ToDateTime > minWindowStart)) at the query level instead of pulling the resource's entire schedule history into memory.

Suggestions

src/Modules/Ems/Ems.Application/Integrations/EventVenueConflict/EventVenueConflictHandler.cs:58-77

N+1 evaluation per event venue. GetResourceScheduleConflictMessageKeyAsync loops over each internal venue and issues a separate sender.Send(new EvaluateResourceScheduleStatusQuery(...)) sequentially, each of which triggers its own resource-master lookup, schedule query, and (on conflict) status lookup. This handler runs per workflow transition on the event request, so an event with several internal venues means several sequential round-trips where one batched evaluation (all venues' windows against their resources in a single query) would do.

src/Modules/Rms/Rms.Application/Endpoints/ResourceScheduleEndpoints.cs:256-263

New endpoint missing .SkipActivityLogging(). Every other read-only endpoint in this file (GET /, /calendar, /{id:guid}, /by-reference/..., /by-key/...) calls .SkipActivityLogging(), since the group is wrapped with .WithActivityLogging(ModuleCodes.RMS). POST /evaluate-status is functionally a read (the handler only queries, never writes) but is missing the same call, so it will be logged to the audit trail on every invocation — including the per-venue loop in EventVenueConflictHandler above, which will generate disproportionate audit noise for what's a status check, not a user action.

src/Modules/Ems/Ems.Application/Integrations/EventVenueConflict/EventVenueConflictHandler.cs:73

Duplicated magic string instead of the new constant. Both this file and EventVenueService.EnsureInternalVenueScheduleEligibleAsync hardcode the fallback "ems.eventVenue.validation.unavailableForSchedule" as a string literal, even though this PR adds Rms.Application.Constants.EventVenueScheduleValidationMessageKeys.UnavailableForSchedule with the exact same value for this exact purpose. If Ems.Application can't take a dependency on Rms.Application directly, consider exposing the constant through Rms.Contracts instead so there's one source of truth rather than two hand-kept copies of the same string.

src/Modules/Ems/Ems.Application/Integrations/EventVenueConflict/EventVenueConflictHandler.cs:44-55

Schedule conflict silently discards workflow conflict details. When both a workflow conflict (workflowResponse.HasConflict) and a schedule conflict are present and the workflow isn't next-status-approved, the method builds a brand-new ConflictDetectionResponseDto for the schedule conflict, discarding workflowResponse's own Severity/SuggestedBehavior/Message entirely. If that's intentional (schedule conflicts always take precedence), worth a one-line comment; if not, the caller loses visibility into the original workflow conflict.

Notes

src/Modules/Rms/Rms.Application/Services/ResourceScheduleStatusEvaluator.cs:441-445

Redundant manual validation. EvaluateAsync re-checks ResourceMasterId == Guid.Empty and Windows is null || Count == 0 even though EvaluateResourceScheduleStatusQueryValidator already enforces both via QueryValidationBehavior before the handler runs. Not wrong, just duplicate logic worth trimming if this evaluator is never called outside the MediatR pipeline.

What's Good

Clean CQRS wiring for the new capability. EvaluateResourceScheduleStatusQuery/Handler/Validator follow the established pattern precisely, and the evaluator is properly interfaced (IResourceScheduleStatusEvaluator) and reused from both EMS (cross-module via ISender) and RMS's own venue-eligibility guard, avoiding duplicated conflict logic between the two call sites.

Readable priority-based conflict resolution. GetConflictPriority/worstConflictPriority in ResourceScheduleStatusEvaluator picks the most severe overlapping schedule cleanly, avoiding a nested-if chain.

Graceful handling of missing configuration. BuildAvailableResultAsync falls back sensibly and logs a warning when no default "Available" ResourceStatus is configured for a category, rather than throwing and blocking the whole eligibility check.

Backend validation present for the new write path. EvaluateResourceScheduleStatusQueryValidator covers the required-field and window-ordering rules consistent with how other RMS validators in this module are structured.
