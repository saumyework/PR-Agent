This PR is open. It adds a Request Management KPI counts endpoint in SDM (GetKpiCountsAsync in RequestService). The endpoint returns total, active, resolved, unassigned, high/critical and overdue counts, scoped by company and requester. It also adds Brain docs (daily notes and story board).

Nothing is clearly broken, but the overdue join key (condition.SlaPolicyId == snapshot.Id) is unverified and could make Overdue always 0. The assumptions about ListAsync (an unmaterialised, unpaged IQueryable) and about soft-deleted requests are also unchecked. There are no tests, and the author's notes say the code was not run against a database.

The team should decide whether the frontend work described in the notes is in another PR, and link it if so. The PR description is empty. The performance of the six count queries plus a nested correlated subquery is worth a look before merge.

F1 src/Modules/Sdm/Sdm.Application/Services/RequestService.cs:932

Overdue join key may be wrong. The overdue query joins SlaConditionSnapshot to the policy snapshot with condition.SlaPolicyId == snapshot.Id. If SlaPolicyId holds the live policy id rather than the snapshot id, Overdue will always be 0. Check the entity configuration and fix the join, ideally with a DB-backed test. Also at: src/Modules/Sdm/Sdm.Application/Services/RequestService.cs:933.

F2 src/Modules/Sdm/Sdm.Application/Services/RequestService.cs:855

Unclear ListAsync contract with positional args. The call passes null, false, query, true positionally and treats filtered.Items as an unmaterialised, unpaged IQueryable. If the last flag is not disableSkipTake, or Items is already materialised or paged, the counts are wrong or fail. Use named arguments and confirm the behaviour.

F3 src/Modules/Sdm/Sdm.Application/Services/RequestService.cs:847

Soft-deleted requests may be counted. The base query filters only by CompanyId. The story says Total should be 'Non-deleted requests'. Unless the repository or global query filter excludes IsDeleted, deleted requests are included in every KPI count. Compare with how GetAsync builds its query.

F4 src/Modules/Sdm/Sdm.Application/Services/RequestService.cs:925

Many count queries and heavy overdue subquery. CountOverdueAsync runs, for each request, an Any over snapshots that contains a nested !Any (latest-snapshot check) and another Any over breached conditions. This is a correlated subquery inside a correlated subquery, run over the whole filtered request set on every list reload. The other five counts are also separate round trips. If the user filter was applied through the repository's ListAsync, each count re-applies it. Consider a single grouped aggregate, or joining to the latest snapshot per request. Also confirm that the SlaPolicyId and RequestId columns are indexed. Also at: src/Modules/Sdm/Sdm.Application/Services/RequestService.cs:886.
