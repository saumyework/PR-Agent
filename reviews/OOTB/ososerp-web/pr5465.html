This PR bundles several SDM bug fixes across two areas: Organization Roles admin (assignable-user list, table columns) and the Requests module (form validation for priority/technician/description/emailsToNotify, save-button behavior, breadcrumb text). The user-assignment fetch for organization roles was rewritten to call a shared SdmUserManagementService.getAll() instead of a bespoke license/user-type resolution, and priorityId/technicianId were consistently loosened to optional across form, DTO type, and payload mapping. No hard correctness bugs were found, but several changes alter user-visible or safety-relevant behavior (who shows up as assignable, whether Save is gated by validity) in ways that are plausible intentional fixes but aren't fully verifiable from the frontend diff alone — flagged below as Suggestions for QA/product confirmation.

Suggestions

organization-role-details.component.ts:238

Assignable-user filtering was dropped, not just refactored. The old code resolved a single active, non-super-admin UserType (excluding SUPER_ADMIN_USER_TYPE) and fetched only that type's users via availableUserListAsync. The new code calls this.#userManagementService.getAll(new HttpParams()) (line 238) with no filter at all, so every module user — including any super-admin accounts — now appears in the "assign users" slider for an organization role. If excluding super-admin/inactive accounts from this list was intentional business logic (not just an artifact of the old broken single-type resolution), this is a quiet regression worth confirming with QA/product before merge.

request-detail-page.component.ts:210, create-request-page.component.ts:145

Save-gate relies on an implicit microtask ordering assumption. Both #save() implementations bump a markAsTouched signal and then read validChanges() inside a bare queueMicrotask, assuming Angular's own effect scheduler (which propagates the child form's re-validated status back through the (validChanges) output) flushes within that same microtask turn. It works today, but it's an undocumented reliance on Angular's internal effect-flush timing rather than an explicit signal derivation — a future Angular version or refactor that changes effect scheduling could silently let an invalid form submit with no test failure to catch it. Worth a short comment explaining the ordering requirement, or replacing it with a `computed()`/direct form-status read that doesn't depend on scheduling order.

requests-page.component.html:38,45

Save button disabled state no longer reflects form validity. [disabled]="!validChanges() || saving()" became [disabled]="saving()" for both the create and edit Save buttons, so the button is now always clickable regardless of form validity — correctness is enforced only by the internal validChanges() check inside the microtask-gated #save() (see above). This is a reasonable UX pattern (reveal field errors on submit attempt instead of a silently-disabled button), but it means the button's visual state and its actual behavior are now decoupled; confirm this is the intended UX and not an oversight from removing the old guard.

organization-role-details.component.ts:238

Unbounded fetch on every dialog open. getAll(new HttpParams()) requests the full module user-profile list with no pagination params each time "Assign Users" is opened. This mirrors an existing pattern elsewhere in the module (getRequesters/getTechnicians in request-detail-page.component.ts), so it's not a new anti-pattern, but for tenants with a large user base this is a page that gets opened repeatedly and could become a real Suggestion-to-Must-Fix performance issue as data grows — worth confirming the backend endpoint paginates/caps results by default.

Notes

request.util.ts:44

Fake control cast to reuse a validator. emailsToNotifyValidator calls OsosValidators.email({ value: email } as AbstractControl) — it works because email() only reads .value, but the cast silently bypasses type safety. Extracting the email pattern/length check into a plain function reusable by both validators would avoid faking an AbstractControl.

request-details.component.ts:242-249 (and create-request.component.ts, same pattern)

Redundant validity recompute. #onDescriptionChange calls setValue(value, { emitEvent: false }) immediately followed by updateValueAndValidity({ emitEvent: false }) on the same control — setValue already recomputes validity on its own, making the second call a duplicate no-op pass. Harmless for a single control, but worth trimming.

request-details.component.html:116

Inconsistent error slot for priority. The technicianId select got a new <mat-error [ososError]="formControls.technicianId" />, but the priorityId select right above it (which got the same optional-empty-option treatment) did not. Harmless today since priorityId currently carries no validators, but if one is added later it'll silently show no feedback — worth adding for consistency now.

request.util.ts:8

Import order. import { AbstractControl, ValidationErrors } from '@angular/forms' is placed after the @osos/core import block, inconsistent with the external-then-internal ordering used elsewhere in this same PR (e.g. organization-role-details.component.ts). Husky's pre-commit lint-fix will likely reorder this automatically, but flagging in case it's committed as-is.

What's Good

organization-roles-page.component.ts:104

Genuine dead-code bug fixed. #normalizeColumns(columns) was previously computed but its result was never assigned back to availableColumns$ — the raw, un-normalized columns were pushed instead. That's now wired up correctly, and the "Assigned Users" display-name override and new hierarchy filter/sort flags actually take effect.

End-to-end consistency for optional priority/technician. The relaxation from required to optional was carried through every layer that needed it together: reactive form validators, the SaveRequestPayload.priorityId: string | null type change, and the toOptionalGuid mapping in request.util.ts — no half-applied change left behind.

Validation errors now surfaced instead of silently blocked. Adding mat-error[ososError] for emailsToNotify and description, plus forcing markAllAsTouched() on a failed save attempt, gives users an actual reason when a save doesn't go through instead of a permanently greyed-out button.

New columns added consistently. createdDate/createdBy were added together across the TS DISPLAY_COLUMNS definition, the organization-role.json table config, and both en-US/ar-OM locale files — no missing translation keys.

Simpler, more consistent data-fetch pattern. Replacing the bespoke license-service + user-type-resolution chain with a single call to the already-established SdmUserManagementService.getAll() (used the same way elsewhere in the module for requesters/technicians) removes a fair amount of one-off complexity (#resolveUserType is gone entirely).
