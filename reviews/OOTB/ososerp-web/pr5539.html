This PR migrates the SDM Request detail page from the legacy RequestFormActionService pattern to the shared MasterDetailBasePageComponent / app-master-detail-header pattern, adding workflow status display, comments support, and a rejection flow — closely mirroring how sibling detail pages (e.g. learning-plan-detail-page, decision-detail-page) already do this. It also adds logic to keep the currently-selected requester/technician visible in their dropdowns even if they've dropped out of the active user list, and migrates the request list's status column to the shared getStatusList workflow-status renderer.

The main concern is a stray this.departments(); statement inside a reactive effect() in request-details.component.ts that has no visible purpose but does register departments as an effect dependency — causing the whole form-population routine (including a subcategories HTTP re-fetch) to silently re-run whenever the async department list resolves, which can clobber in-progress user edits. The rest of the migration is well aligned with existing conventions elsewhere in the codebase.

Must-Fix

libs/features/sdm/src/lib/requests/components/request-details/request-details.component.ts:200

Stray signal read over-triggers form-repopulation effect. Inside #populateFormFromRequest (run from an effect() in the constructor), the line this.departments(); reads the signal but never uses the result — its only effect is to register departments as a reactive dependency of the surrounding effect. Since departments is fed by an async toSignal(...) in the parent that starts at [] and later resolves to the real list, this effect will fire a second time once departments load, even if selectedRequest()/detail() haven't changed. That second run re-executes patchValue/setValue on the whole form and re-triggers #loadSubCategories (an HTTP call) via #applyLoadedFormMode/#loadSubCategories. On every page load this wastes a redundant subcategories fetch, and if the user starts editing the form before the department list resolves (slow network), their in-progress edits get silently overwritten when the effect re-runs and repatches from selectedRequest(). Either remove the dead read, or if it's intentionally forcing a re-render for the department to pick up newly-available options, replace it with a narrower, documented mechanism that doesn't reset the whole form.

Suggestions

libs/features/sdm/src/lib/requests/components/request-details/request-details.component.ts:229

Synthetic UserProfile is missing ~25 required fields. #withSelectedUserProfile prepends a fabricated entry ({ id, userId, user: { fullName } } as UserProfile) when the request's requester/technician isn't in the fetched list. UserProfile (libs/core/src/lib/core/models/user-profile.ts) has ~25 other non-optional fields (company, email, imagePath, status, etc.) that are silently undefined on this synthetic object. The as UserProfile cast bypasses TypeScript's structural check entirely. It's safe today because the template only reads item.id/item.user.fullName, but any future consumer of requesterOptions()/technicianOptions() that reads more (avatar, email, company) will get undefined without a compile error to warn them.

libs/features/sdm/src/lib/requests/components/request-details/request-details.component.ts:239

Raw GUID can leak into the dropdown label. In the synthetic profile, user: { fullName: selectedName?.trim() || resolvedId } falls back to displaying the raw profile ID string as the "name" when no name could be resolved. Users would see a GUID instead of a human-readable label in the requester/technician dropdown for that edge case.

libs/features/sdm/src/lib/requests/components/request-details/request-details.component.ts:265

Fragile name-based identity resolution. #resolveUserProfileId falls back to matching a profile by lowercased/trimmed fullName when no ID matches. Two users with the same display name would resolve to whichever happens to match first, silently picking the wrong requester/technician. Preferring the backend-supplied ID everywhere (and treating name-matching as a last resort with a warning, or not falling back at all) would be more robust.

libs/features/sdm/src/lib/requests/components/request-details/request-details.component.ts:212

Redundant setValue calls right after patchValue. this.inputForm.patchValue(formValue, ...) already sets requesterId/technicianId/departmentId (they're part of formValue), but the next three lines immediately call setValue on those same three controls again with the same values. If this is working around a Material mat-select rendering quirk, a short comment would save the next reader from re-deriving why; if not, it's dead duplication.
