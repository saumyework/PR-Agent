Single-file, surgical fix (+6/-47) in requests-list-page.component.ts for the SDM Requests list's "fixed columns move after saving the column selection" bug. The component's overridden setAvailableColumns previously re-implemented a custom merge of saved column metadata against live column defaults via a private #mergeColumnMetadata helper; that's deleted and replaced with a direct delegation to super.setAvailableColumns(). Verified against the actual base branch (feature/ems-rms-sdm/OOTB-011, not the repo's default branch) that MasterListBasePageV1Component.setAvailableColumns is protected (not private) there, so the override and super call are valid and this compiles.

This change brings the component's saved-column-selection handling in line with the base class's standard behavior, which is what every other MasterListBasePageV1Component subclass in the repo already relies on unmodified — so it's a consistency fix, not a novel pattern. The PR's checklist is entirely unchecked (no confirmation of local testing, no unit tests added, and this component has no existing spec file), so it's worth a manual sanity check that the specific "fixed columns reordering" scenario from the ticket no longer reproduces before merging.

libs/features/sdm/src/lib/requests/containers/requests-list-page/requests-list-page.component.ts:155

Saved column metadata no longer refreshed against live defaults. The removed #mergeColumnMetadata used to re-apply the current path, allowSearch, allowSort, allowFilter, allowedFilters, dataType, and isInsideObject from ColumnDetailsService onto whatever the user had previously saved, and appended any brand-new default columns that weren't part of the saved selection. Delegating straight to super.setAvailableColumns() drops that merge — saved metadata is now used exactly as stored, with no top-up from live defaults. This matches how the base class behaves for every other list page in the repo (confirmed in master-list-base-page-v1-component.ts:826-836 on this PR's base branch), so it's likely the intended tradeoff, but it does mean a future change to a column's capabilities (e.g. making a column sortable) won't retroactively reach users who already have a saved selection for this table, and newly-added default columns won't surface for them either until they reset their selection.

libs/features/sdm/src/lib/requests/containers/requests-list-page/requests-list-page.component.ts:159-164

Duplicate re-implementation of the base class's "no saved columns" path. When userColumnsFromDb?.metadata is falsy, this block fetches columnSelectionJsonService.getColumnDetails(TableType.SdmRequest) and pushes the result straight to availableColumns$ — which is exactly what super.setAvailableColumns(userColumnsFromDb) already does internally when given a falsy/no-metadata value (using this.options.constants.tableType, which is already set to TableType.SdmRequest in the constructor). The only real reason for this override to exist at all is to guard against an object with an empty-string metadata, which would otherwise reach the base's JSON.parse and throw. Consider narrowing the override to just that guard (e.g. only special-case an empty metadata string, otherwise delegate unconditionally) to avoid maintaining two copies of the same default-fetch logic.
