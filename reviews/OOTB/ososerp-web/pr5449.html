Adds a new "Request History" tab (grid/timeline + paginated list views, filters, export-to-file) to the SDM request detail page, plus a separate feature that locks form fields left empty at request creation time so they can't be edited later. The lock-on-empty logic in request-details.component.ts is clean, well-encapsulated, and signal-driven. The new history component, however, largely re-implements the existing shared app-history component (libs/shared/components/.../history/history.component.ts) rather than reusing it, and in doing so introduces two concrete display bugs: table column headers/action-type labels use translation keys that don't exist in either locale file, and the grid-view action badges compare against action-string casing that doesn't match the app's own established convention. Both would be immediately visible to a QA pass on the new tab.

Errors Warnings Notes Passed

Must-Fix

libs/features/sdm/src/lib/requests/constants/request-history.constants.ts:22-43

Missing translation keys in both locale files. The table column headers use translation.configuration.logs.columnheader.action, .user, .description, and .performedDate, and the grid-view badges (request-history.component.html:221-238) use translation.configuration.logs.label.created/updated/deleted. None of these keys exist anywhere in src/assets/i18n/en-US.json or ar-OM.json (confirmed via search) — the only strings this PR touched in those two files are an unrelated requests.title.add change. With ngx-translate, missing keys render the raw key string, so the new "Request History" table headers and action badges will show literal translation.configuration.logs.columnheader.action-style text instead of "Action"/"User"/etc.

libs/features/sdm/src/lib/requests/constants/request-history.constants.ts:127-131

Action-badge switch will never match a real log entry. This PR defines HISTORY_LOG_ACTION = { CREATE: 'Create', UPDATE: 'Update', DELETE: 'Delete' }, used in request-history.component.html:221-238 as @switch (log.action) { @case (LOG_ACTION.CREATE) ... }. But the very same PR also copies the codebase's established ActionType enum into request-history.component.ts:89-92 (DELETE = 'DELETE', ADD = 'ADD', UPDATE = 'UPDATE') — an exact copy of the enum already used in production against real history.action values in libs/shared/components/.../history/history.component.ts. That proves the backend actually returns upper-case values like 'DELETE'/'ADD' (not 'Create'/'Delete', and never 'CREATE' at all — the backend uses 'ADD'). As written, none of the three @case branches in the grid view can ever match, so the colored Created/Updated/Deleted badges will never render for any history entry.

Suggestions

libs/features/sdm/src/lib/requests/components/request-history/request-history.component.ts

Large duplication of the existing shared history component. getLogs, getExtendedLogs, toggleFilters, search, typeChange/timePeriodChange, modifyDescription, #disableInnerLog, and #findChangedProperties are near line-for-line copies of the equivalent methods in libs/shared/components/src/lib/shared-components/history/history.component.ts (the existing app-history dialog component). Per the Angular guide's "use reusable components" checklist and the general DRY guideline, consider extracting the shared fetch/filter/diff logic into a service or base class both components consume — the translation-key and casing bugs above are exactly the kind of drift this duplication invites, since a fix in one copy won't propagate to the other.

libs/features/sdm/src/lib/requests/components/request-history/request-history.component.ts:874

Missing OnPush change detection. SdmRequestHistoryComponent renders a paginated data table and, in grid mode, a timeline of potentially many entries with nested loops, images and multiple pipes, but doesn't set changeDetection: ChangeDetectionStrategy.OnPush. Given this is a tab on the request-detail page (opened frequently), OnPush plus the existing signal-based state would avoid unnecessary change-detection passes.

libs/features/sdm/src/lib/requests/components/request-history/request-history.component.html:154-521

Grid view has no pagination. The List view is paginated via app-datatable-v1/listPageEvent, but the Grid (timeline) view renders every entry in histories() unbounded inside .timeline-scroll-container. For a request with a long edit history this can render hundreds of DOM nodes (each with an image, badges, and multiple pipes) in one pass whenever a user toggles to grid view. Consider paginating or virtualizing the grid view the same way the list view already is.

libs/features/sdm/src/lib/requests/components/request-history/request-history.component.ts:441-460

Export failures are silent. #handleFileExport's call to #historyService.exportActivityLogs(...) has no catchError/error handler on the subscription. If the export request fails, the user clicks "Export", nothing downloads, and no error is surfaced — they have no way to know it failed versus still being in progress.

libs/features/sdm/src/lib/requests/components/request-history/request-history.component.ts:167-176

Timeline grouping key uses UTC, display uses tenant timezone. groupedLogs buckets entries by new Date(log.dateTime).toISOString().split('T')[0] — a UTC calendar day — while each entry's own displayed time goes through the timeZoneDate pipe (tenant/local time) and the group header goes through relativeDate. For a timezone like Oman (UTC+4), an entry near local midnight can end up grouped under the wrong day relative to the time actually shown for it. Consider deriving the group key from the same local-timezone date used for display.
