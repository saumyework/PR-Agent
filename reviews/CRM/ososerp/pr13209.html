Refactors CRM Team endpoints/service off the old IUserTeamService/IPrivilegedUserService/ICompanyContextService dependencies, moving the request-scoped concerns (user id, company id) into the handlers via BaseHandler and injecting entity repositories directly into TeamService. It also converts TeamQueryHelper static helpers into proper extension methods and inlines the endpoint delegates to match the pattern already used elsewhere (e.g. VenueEndpoints.cs).

The refactor drops audit-field stamping (CreatedBy/CreatedDate/UpdatedBy/UpdatedDate) on Team create/update and on the new user-team auto-assignment path, even though the relevant userId is still threaded through the call chain — it's just never applied. That's a silent data-integrity regression across every future Team write, which is why this lands at High risk despite being a fairly mechanical-looking refactor.

Errors Warnings Notes Passed

Must-Fix

src/Modules/Crm/Crm.Application/Services/TeamService.cs

Team create/update no longer stamps audit fields. The private CreateTeamAsync(Team team) and ModifyTeamAsync(Team team) helpers used to set CreatedBy/CreatedDate and UpdatedBy/UpdatedDate respectively (confirmed on the base branch), but in this refactor those assignments were dropped entirely — the methods just call repository.AddAsync/UpdateAsync on the entity as-is. CreateTeamFromRequestAsync and ModifyTeamFromRequestAsync both still receive userId as a parameter and use it elsewhere (rollback on circular-hierarchy, cascading user-team logic), but never assign it to the entity anymore. Every new/updated Team row will now persist with an empty/default CreatedBy/UpdatedBy and default DateTimeOffset for the corresponding date fields.

src/Modules/Crm/Crm.Application/Services/TeamService.cs

Auto-assigned UserTeam rows lose audit fields and validation. The new private BulkCreateUserTeamsAsync(IEnumerable<UserTeam> userTeams) (used by HandleUserTeamAssignmentAsync/HandleUserTeamReassignmentAsync when a team gets a new manager chain) only sets IsActive = true before calling userTeamRepository.AddAsync — it no longer sets CreatedBy/CreatedDate, and skips the ValidateUserTeamOnCreate/ValidateStorageUserTeam checks that the sibling UserTeamService.BulkCreateUserTeamsAsync(userTeams, userId) still performs for every other caller in the module. The old code routed through userTeamService.BulkCreateUserTeamsAsync(newUserTeams, userId) and got both the stamping and the validation for free; this new in-class reimplementation gets neither.

Suggestions

Create/Delete/Update/GetTeamLookUp Handlers

Company-id resolution duplicated across four handlers. CreateTeamHandler, DeleteTeamHandler, UpdateTeamHandler, and GetTeamLookUpHandler each independently do await sender.Send(new CompanyByCodeQuery(CompanyCode), cancellationToken) and then read company.Company.Id. It's the same line copy-pasted four times, and it's a wider divergence from how ITeamService used to own this concern (previously encapsulated behind ICompanyContextService.GetCompanyIdAsync() inside TeamService itself, not spread across every handler). Note company.Company can genuinely be null (the underlying CompanyService.GetAsync(companyCode) returns null when no match is found) — matching an existing (if risky) pattern already present in WorkflowService, so it's not a new class of bug, but worth consolidating rather than repeating four times.

src/Modules/Crm/Crm.Application/Services/TeamService.cs

TeamService now reimplements logic owned by sibling services. IUserTeamService/IPrivilegedUserService/IUserInformationService are still present and actively used elsewhere in the CRM module (e.g. UserTeamService.cs is untouched by this PR), but TeamService now bypasses them and talks directly to IRepository<UserTeam>/IRepository<PrivilegedUser>/IRepository<UserInformation>, duplicating BulkCreateUserTeamsAsync/RemoveRangeUserTeamsAsync in-class. Beyond the audit-field bug flagged above, this means the two implementations can silently drift — any future validation/business-rule change to UserTeamService won't apply to teams created through this path. Consider keeping cross-aggregate writes behind the existing services instead of duplicating them here.

Notes

GetUserTeamHierarchicalResponseHandler.cs

Inconsistent with its four sibling handlers in this same PR. CreateTeamHandler, DeleteTeamHandler, UpdateTeamHandler, and GetTeamLookUpHandler were all updated to extend BaseHandler(httpContextAccessor), but this handler still takes IHttpContextAccessor directly and manually reads the IS_TEAM_MANAGER_HEADER header inline instead.

What's Good

TeamEndpoints.cs

Endpoint style now matches the rest of the codebase. Inlining the route delegates instead of named private static methods brings this file in line with the convention already used in e.g. VenueEndpoints.cs.

TeamExtensions.cs

Proper extension-method mapping. Converting TeamQueryHelper's static MapXxx methods into this-parameter extension methods (ToEntity(), ToListResponse(), etc.) is a nice readability win and matches the DTO-mapping style shown in the team's own C# guide.

TeamService.cs — GetTeamLookUpAsync

Genuine multi-tenancy fix. GetTeamLookUpAsync now actually filters by x.CompanyProfileId == resolvedCompanyId; previously companyId was fetched but never used to scope the query.

ITeamService.cs

Tighter public surface. Dropping unused public members (RetrieveAllTeams, BulkCreateTeamsAsync, ModifyRangeTeamsAsync, RemoveRangeTeamsAsync, etc.) from the interface reduces what callers outside the service can reach into, now that they're correctly private implementation details.
