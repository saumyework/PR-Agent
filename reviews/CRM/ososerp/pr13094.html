pbsgears/ososerp #13094 Chalaka Karunarathne feature/crm/CM-3043-architecture-migration ← develop/crm/chalaka-subcategory-classification-refactor 2026-07-24

Large CRM architecture migration (127 files changed; the reported 63k additions are almost entirely 8 auto-generated EF Core migration Designer.cs snapshot files, ~7,500 lines each — the hand-authored diff is closer to a few thousand lines). The PR moves CRM's CustomDataSource/CustomDataCategory/CustomDataSubCategory/SubCategoryClassification/SystemConfiguration endpoints off a "fat service" pattern and onto CQRS (MediatR Commands/Queries/Handlers/FluentValidation validators per use case), and removes the bilingual SecondaryName field across the whole vertical. The CQRS migration itself is well executed and consistent with the team's guide. However, verifying the refactor against the code it replaced turned up a confirmed cross-tenant data leak and a few silent regressions (lost audit fields, lost list search/filter/sort, inconsistent user-id validation) that should be fixed before merge.

Must-Fix

src/Modules/Crm/Crm.Application/Services/CustomDataSourceService.cs (GetAllCustomDataSourceAsync)

Cross-tenant data leak. GetAllCustomDataSourceAsync() resolves companyId via GetCompanyIdFromContextAsync() but never uses it — the repository query is just x => !x.IsDeleted. GET crm/CustomDataSource now returns every company's custom data sources to any authenticated user, not just the caller's own company. Compare CustomDataCategoriesService.GetAllCustomDataCategoriesAsync in the same PR, which correctly filters on x.CustomDataSource.CompanyProfileId == companyId — that's the pattern this method is missing.

src/Modules/Crm/Crm.Application/Endpoints/SystemConfigurationEndpoints.cs, SystemConfigurationQueryHelper.cs, Services/SystemConfigurationService.cs

Lost search/filter/sort/group-by on System Configuration list. The old endpoint accepted BaseFilterDtoPaginated baseFilter and ran it through ApplySearch/ApplyFilters/ApplySort/GetGroupKeySelector (~120 lines, all deleted from SystemConfigurationQueryHelper.cs). The new GetAllQuery → GetAllHandler → SystemConfigurationService.GetAllSystemConfigurationsAsync() takes no parameters at all and just paginates the unfiltered set. If the Angular list page still sends search text, column filters, sort, or group-by, they'll now be silently ignored server-side. The same shape of regression applies to CustomDataSourceService.GetAllCustomDataSourceAsync(), whose interface also dropped its BaseFilterDtoPaginated parameter.

src/Modules/Crm/Crm.Application/Services/SystemConfigurationService.cs (RemoveSystemConfigurationAsync)

Soft-delete no longer records who/when. This method now only sets IsDeleted = true; IsActive = false; — DeletedBy and DeletedDate are never assigned. Every sibling service touched in this PR (CustomDataCategoriesService, CustomDataSourceService, CustomDataSubCategoryService, SubCategoryClassificationService) still sets both fields on delete, so this looks like an isolated miss rather than an intentional change.

src/Modules/Crm/Crm.Application/Services/SubCategoryClassificationService.cs

No user-id validation before writes. Every create/update/delete/status-change method here reads var userId = UserId; and uses it directly with no guard. The sibling CustomDataCategoriesService and CustomDataSubCategoryService in this same PR both introduced a GetRequiredUserId() helper that throws BadRequestException when UserId == Guid.Empty (replacing the old endpoint-level "User id is required" checks). This class dropped that check entirely — if the auth context ever fails to populate a user claim, CreatedBy/UpdatedBy/DeletedBy will silently be written as Guid.Empty instead of the request failing fast.

Suggestions

src/Modules/Crm/Crm.Application/Endpoints/CustomDataSourceEndpoints.cs, CustomDataCategoriesEndpoints.cs, SystemConfigurationEndpoints.cs

Route casing is inconsistent and violates the team's naming guide (camelCase plural route segments): app.MapGroup("crm/CustomDataSource"), app.MapGroup("crm/CustomDataCategories"), and app.MapGroup("crm/SystemConfiguration") all use PascalCase, while app.MapGroup("crm/subCategoryClassification") (also touched in this PR) correctly uses camelCase. Suggest normalizing to crm/customDataSource, crm/customDataCategories, crm/systemConfiguration per guides/C#_Code_Review.txt §5.1.1 — worth doing now before any frontend/API-consumer code hard-codes the new casing.

src/DbMigrator/DataMigrations/Crm/Crm_InitialMigration.cs (SeedCustomDataSourcesAsync)

The three seeded CustomDataSource rows now set CompanyProfileId = Guid.Empty. Once the tenant-scoping bug above is fixed, queries that filter on the real CompanyProfileId will make these seed rows invisible to every company. Consider seeding a real/placeholder company id, or documenting why Guid.Empty is intentional (e.g. a "global" pseudo-tenant that's actually handled somewhere).

src/DbMigrator/appsettings.json

ConnectionStrings:PostgreSQL:Database changed from osos-new-new-test-24 to osos-new-36. This reads like a personal local dev database name rather than an intentional shared config change — worth double-checking it isn't accidental, since it'll silently apply to whoever pulls this branch next.

src/Modules/Crm/Crm.Application/Services/CustomDataSourceService.cs (RemoveCustomDataSourceFromRequestAsync)

Delete cascades soft-delete to immediate child CustomDataCategory rows only (SoftDeleteCategoriesAsync) — it doesn't reach further down to CustomDataSubCategory or SubCategoryClassification rows under those categories. If those are expected to stay queryable/active independent of their deleted ancestor that's fine, but if not, this can leave orphaned "active" sub-records under a deleted source.
