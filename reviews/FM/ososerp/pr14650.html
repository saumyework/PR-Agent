This PR converts the Fleet masters (Department, JobTitle, OperatorType, VehicleSource, InspectionCheckList) to the new module. It adds endpoints, commands, queries, validators, services, DTOs, mapping extensions and localization keys, plus source-visibility scoping for departments and sources.

Nothing is a certain crash, but several issues should be fixed before merge. The company lookup trusts a caller-supplied CompanyId, a possible cross-tenant leak. Source visibility fails open when config is missing. Source delete has no in-use check or cascade. Create validators trust a client-supplied Id in uniqueness checks. Sync logic silently turns unmatched ids into new rows. The PR is also very large (about 5000 lines, 159 files) and should have been split. It has an empty description and no visible tests.

The team should decide whether the company lookup is meant to be cross-company, and whether the fail-open source visibility is the intended legacy behaviour.

Method: 9 independent review calls over 3 shard(s), evidence machine-checked (1 unverifiable candidates discarded), then one merge call.

F1 src/Modules/Fleet/Fleet.Application/UseCases/Departments/Queries/GetCompanyLookup/GetDepartmentCompanyLookupQueryHandler.cs:19

Company lookup trusts caller-supplied CompanyId. GetDepartmentCompanyLookupQueryHandler passes the request's CompanyId straight to the service with no tenant check. Sibling department handlers resolve the company from CompanyCode. Any authenticated user can list another tenant's departments by sending that company's id. Resolve the company from the caller, or add an explicit authorization check if cross-company access is intended.

F2 src/Modules/Fleet/Fleet.Application/UseCases/Departments/Commands/Create/CreateDepartmentCommandValidator.cs:36

Create uniqueness check trusts client Id. The create validators call IsNameUniqueAsync(dto.Id, dto.Name), and the id is presumably used to exclude the record's own row. On create the id comes from the request body. A caller who sends the Id of an existing record can create a duplicate name, because that record is excluded from the check. A caller can also pass an Id that collides with an existing row. The create validators should pass Guid.Empty, or the create DTO should not accept an Id. The same pattern is in CreateJobTitleCommandValidator, CreateOperatorTypeCommandValidator, CreateVehicleSourceCommandValidator and CreateInspectionCheckListCommandValidator.

F3 src/Modules/Fleet/Fleet.Application/Services/SourceVisibilityService.cs:62

Source visibility fails open on missing config. Several branches grant unrestricted access when data is missing. GetRestrictedSourceIdsAsync returns null (unrestricted) when moduleKey is blank. It also returns null when the user is a fleet-source user without a fleet source id. IsAllSourcePermissionAsync returns true when the permission module or the permission row is missing. GetDepartmentListScopeAsync returns Unrestricted when the user has no source and no contact. A caller that omits or mistypes moduleKey, or a missing permission row, silently exposes all sources and departments. Confirm this is the intended legacy behaviour. If not, deny by default. Also at: src/Modules/Fleet/Fleet.Application/Services/SourceVisibilityService.cs:54, src/Modules/Fleet/Fleet.Application/Services/SourceVisibilityService.cs:144.

F4 src/Modules/Fleet/Fleet.Application/UseCases/VehicleSources/Commands/Delete/DeleteVehicleSourceCommandValidator.cs:19

Source delete lacks in-use check and cascade. Delete validators for Department (IsInUseAsync), JobTitle, OperatorType and InspectionCheckList (IsUsedByActiveInspectionAsync) all block deleting rows that are still referenced. The VehicleSource delete only checks existence. The Source entity has SourceVehicles, ContactSources, SourceCompanies, SourceUsers and DepartmentSources. Deleting a source that vehicles or contacts still reference could orphan data or hit an FK error. Add an in-use rule consistent with the siblings, or confirm the service cascades or handles this. Also at: src/Modules/Fleet/Fleet.Application/UseCases/VehicleSources/Commands/Delete/DeleteVehicleSourceCommandValidator.cs:20, src/Modules/Fleet/Fleet.Application/Services/VehicleSourceService.cs:158, src/Modules/Fleet/Fleet.Application/Services/VehicleSourceService.cs:154.

F6 src/Modules/Fleet/Fleet.Application/Services/VehicleSourceService.cs:126

Create and Update differ releasing fleet source. UpdateAsync passes shouldRemovePermissions: true when another source becomes the fleet source. CreateAsync passes false. The previous fleet source then keeps its active SourcePermission rows after losing IsFleetSource. Make the two paths consistent. F7 src/Modules/Fleet/Fleet.Application/Services/VehicleSourceService.cs:214

Unmatched ids in sync become new rows. Incoming permissions, sections, questions and choices whose Id is non-empty but not found among the active children are treated as new rows. This hides stale or foreign ids instead of returning NotFound or validation errors. Locations: VehicleSourceService.SyncPermissionsAsync, and InspectionCheckListService.SyncSections, SyncQuestions and SyncChoices. Duplicate incoming ids are also not rejected, so the same child can be applied twice. Also at: src/Modules/Fleet/Fleet.Application/Services/InspectionCheckListService.cs:169.

F8 src/Modules/Fleet/Fleet.Application/Services/InspectionCheckListService.cs:126

Checklist soft delete does not cascade fully. DeleteAsync marks only the sections as Removed. Questions and choices stay Active. SyncSections has the same gap: a removed section keeps its Active questions, and SyncQuestions leaves a removed question's choices Active. Any query that reads FormQuestion directly will still see them. Also, DeleteAsync does not itself check IsUsedByActiveInspectionAsync. Confirm the handler does.

F9 src/Modules/Fleet/Fleet.Application/Services/DepartmentService.cs:129

Code generation is racy. GetUniqueCodeAsync reads existing codes and picks the next free one without updating codeSetup.SerialNo and without a lock or unique index. Two concurrent creates can get the same code. The fallback random code in GenerateFallbackCodeAsync, and VehicleSourceService.GenerateUniqueCodeAsync, use the same check-then-insert pattern. Add a unique index on Code, or retry on conflict.

F10 src/Modules/Fleet/Fleet.Application/Services/DepartmentService.cs:210

Tracked loads omit child includes. For tracked loads (UpdateAsync, DeleteAsync) includes is null, so DepartmentSources (and likewise Source children in VehicleSourceService.GetEntityAsync) are not loaded. If ApplyTo syncs those collections, it will see an empty list. That would duplicate existing links and fail to remove old ones. Verify what ApplyTo does. InspectionCheckListService loads the detail includes for tracked loads.

F11 src/Modules/Fleet/Fleet.Application/UseCases/InspectionCheckLists/Commands/InspectionCheckListSectionValidator.cs:24

Referenced ids not checked for existence. FormQuestionTypeId is only checked with NotEmpty, so a random GUID passes validation. Request DTO fields dereferenced without null guard. ToEntity/ApplyTo call .Trim() on dto.Name and DepartmentShortCode. F14 src/Modules/Fleet/Fleet.Application/Endpoints/DepartmentEndpoints.cs:44

Delete returns Ok(bool); Location is relative.
