This PR adds a full CQRS-based CRUD module (DocumentCodeSetupService + Create/Update/Delete/Ensure commands, four queries, endpoints, DTOs) for company-level document numbering setups, replacing the old ad-hoc ProvisionDocumentCodeSetupsAsync method that previously lived on CompanySettingService. The new module itself follows the codebase's established CQRS/folder conventions cleanly, and every write command has a matching FluentValidation validator.

The diff also carries regressions unrelated to the stated ticket scope: it silently drops the existing approval-group provisioning logic from CompanySettingService with no replacement, it strips eager-loading includes from the unrelated VehiclePlateService, and it commits what looks like a local developer's database name/password into the shared DbMigrator/appsettings.json. Within the new feature itself, the lookup endpoint isn't scoped by company (confirmed: FleetDbContext has no global tenant query filter, only schema/JSON-column conventions via ApplyModuleConventions), and soft-deleted document code setups remain readable and editable after "deletion." This diff is unchanged from what v3 reviewed — v1 through v3 remain at pr14111.html, pr14111-v2.html, pr14111-v3.html; findings here match v3 after independent re-verification against the current PR head.

Suggestions

src/Modules/Fleet/Fleet.Application/UseCases/DocumentCodeSetups/Commands/Create/CreateCommand.cs:15-26

No duplicate guard on Create. EnsureForCompanyAsync dedupes by (CompanyId, CodeModuleId) when auto-provisioning, but CreateCommandValidator/DocumentCodeSetupService.CreateAsync has no equivalent check, so POST documentCodeSetups can create two active setups for the same company + module, leaving it ambiguous which one's numbering sequence applies.

src/Modules/Fleet/Fleet.Application/UseCases/DocumentCodeSetups/Commands/Create/CreateCommand.cs:17-25

Numbering fields go unvalidated. Neither CreateCommandValidator nor UpdateCommandValidator checks SerialNo or FormatLength. A zero or negative value for either is accepted and will produce malformed generated document numbers downstream.

src/Modules/Fleet/Fleet.Application/Dtos/DocumentCodeSetupDto.cs:42-57

One DTO serves both request and response. CodeModuleShortCode is populated on the way out (MapToDto) but silently ignored by ToEntity/ApplyTo on the way in. It's harmless today, but a client could reasonably assume setting it on a create/update request has an effect. Consider splitting into a request DTO and a response DTO.

Notes

src/Modules/Fleet/Fleet.Application/Services/DocumentCodeSetupService.cs:44-74

Ensure has a provisioning race window. EnsureForCompanyAsync reads existing setups, computes the missing modules, then inserts — two concurrent calls for the same company (e.g. a double-submit) could both pass the check and insert duplicate rows for the same module. Low impact since this only runs once per company in the normal flow.

What's Good

Consistent CQRS structure. The new UseCases/DocumentCodeSetups/{Commands,Queries}/<Action>/ folder layout and short CreateCommand/GetAllQuery-style naming match the existing CompanySettings use cases exactly, not the more verbose examples in the C# guide — this PR is following the codebase's actual current convention.

NotFoundException used consistently. GetByIdAsync, UpdateAsync, DeleteAsync, EnsureHandler and GetByCompanyIdHandler all throw a proper NotFoundException instead of returning null/silently no-oping.

Format sync avoids hard deletes. SyncFormatsAsync correctly adds new formats, updates matched ones, and soft-removes the rest instead of physically deleting rows, matching the rest of the module's soft-delete convention.

Nested Formats validated via RuleForEach. Both CreateCommandValidator and UpdateCommandValidator validate each item in DocumentCodeSetup.Formats, not just the top-level fields.
