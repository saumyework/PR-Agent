This PR adds full CRUD for DocumentCodeSetup ("Company code setup") in the Fleet module. It includes a new DocumentCodeSetupService/IDocumentCodeSetupService, Create/Update/Delete/Ensure commands, GetAll/GetById/GetByCompanyId/GetActiveLookup queries, a DocumentCodeSetupEndpoints group, DTOs, mapping extensions, and three new localized messages. Document-code provisioning moves out of CompanySettingService into EnsureForCompanyAsync. The unused approval-group provisioning code is removed. Some unrelated VehiclePlate cleanup is also included.

Change since v5: the previous Must-Fix is resolved. UpdateCommandValidator now runs the company + module duplicate check and passes its own Id as excludeId. The remaining blocker is that neither validator checks Status. Because of that, a client can create a setup that is already Removed, or save an undefined enum value.

Errors Warnings Notes Passed

Must-Fix

src/Modules/Fleet/Fleet.Application/UseCases/DocumentCodeSetups/Commands/Create/CreateCommand.cs:18

Status is never validated. DocumentCodeSetupRequestDto.Status (and DocumentFormatDto.Status) is copied straight onto the entity by ToEntity/ApplyTo, but neither CreateCommandValidator nor UpdateCommandValidator has a rule for it. Two ways this goes wrong: (1) a POST with "status": Removed saves the row, then CreateAsync calls GetByIdAsync (DocumentCodeSetupService.cs:130), which filters on Status != Removed and throws NotFoundException. The client gets a 404 even though the record was written. The same path through PUT soft-deletes the setup but leaves its formats active, so it skips the cleanup in DeleteAsync. (2) An integer outside the Status enum is saved as-is. Add RuleFor(x => x.DocumentCodeSetup.Status).IsInEnum() and a rule that rejects Status.Removed to both validators and to the format child rules. Removal should only go through DELETE.

Suggestions

src/Modules/Fleet/Fleet.Application/UseCases/DocumentCodeSetups/Queries/GetActiveLookup/GetActiveLookupHandler.cs:22

Lookup crashes on an unknown company code. company.Company.Id is read without a null check on the result of CompanyByCodeQuery(CompanyCode). A missing or unknown CompanyCode header then throws a NullReferenceException, which reaches the client as a 500. The other handlers in this PR (GetByCompanyIdHandler, EnsureHandler) check for null and throw NotFoundException(nameof(Company), ...). This handler should do the same.

src/Modules/Fleet/Fleet.Application/Services/DocumentCodeSetupService.cs:211

Unknown format IDs are silently ignored. In SyncFormatsAsync, an incoming DocumentFormatDto may have a non-empty Id that doesn't match any active format on this setup (stale ID, or a format from another setup). The loop just continues. The client gets a 200 and assumes the edit was saved, but it was discarded. Either return a validation failure or treat the format as new. (Carried over from v5, still present.)

src/Modules/Fleet/Fleet.Application/Endpoints/DocumentCodeSetupEndpoints.cs:27

Location header has no leading slash. Results.Created($"documentCodeSetups/{...Id}", ...) is missing the leading /. The sibling VehiclePlateEndpoints.cs uses $"/vehiclePlate/{...Id}". Without the slash the Location header is relative, so clients resolve it against the current request path instead of the API root. (Carried over from v5, still present.)
