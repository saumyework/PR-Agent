Adds an RdmLookupValueConfiguration to the InventoryManagement context so EF maps RdmLookupValue.RdmLookupType through the real LookupTypeId column instead of an inferred shadow RdmLookupTypeId column that doesn't exist. This is needed for the Goods Receipt Voucher Type lookup. It regenerates both providers' snapshots with an empty (snapshot-only) AddLookupTable migration. Risk: Low. The shared tables are ExcludeFromMigrations, so there is no DDL and no data impact, and the change fixes a runtime bug.

Nothing blocks merge. The main follow-ups: the migration name is misleading (F1); the root cause lives in the shared entity and still affects seven other modules (F2); the same entity's Company relationship is also mis-inferred here (F3); and unrelated Department snapshot drift is bundled in without mention (F4). Generated *.Designer.cs files were skipped as generated, and every other file was reviewed.

Process: 3 independent review passes plus 1 gap pass. The gap pass's only addition, "staircase" indentation, was dropped because it matches this module's sibling configurations, so the last pass came back with nothing substantive.

F1 src/Modules/InventoryManagement/InventoryManagement.Infrastructure/Migrations/PostgreSQL/InventoryManagement/20260927202810_AddLookupTable.cs:8

Migration name says it adds a table, but it adds none. Both AddLookupTable migrations (PostgreSQL and SqlServer 20260927202839_AddLookupTable.cs:8) have empty Up/Down. F2 src/Modules/InventoryManagement/InventoryManagement.Infrastructure/Data/Configurations/RdmLookupValueConfiguration.cs:23

Fixes a shared-entity bug one module at a time. The real cause is in Shared.Domain.Models.RdmLookupValue: the navigation RdmLookupType and the FK LookupTypeId don't match EF's naming convention. So every context that pulls in the entity without its own configuration invents a shadow RdmLookupTypeId column, and that column doesn't exist in EnterpriseDataManagement.RdmLookupValues. Sdm already has an identical copy of this configuration, and this PR adds a second one. Code search still finds RdmLookupTypeId in the snapshots of Sms, Lnd, JobPortal, Appraisal, Attendance, Recruitment and ExpenseManagement, so they carry the same latent "column does not exist" failure. The entity already uses [ForeignKey("CompanyId")] for Company. Adding [ForeignKey(nameof(LookupTypeId))] to the RdmLookupType navigation would fix every context at once and make these per-module configurations unnecessary. This is fine to merge as a module-local fix, but raise a follow-up ticket.

F3 src/Modules/InventoryManagement/InventoryManagement.Infrastructure/Migrations/PostgreSQL/InventoryManagement/InventoryManagementPostgresDbContextModelSnapshot.cs:1676

Company relationship on the same entity is still mis-inferred. This file exists to correct an EF convention guess on RdmLookupValue, but it leaves a second wrong guess on the same entity. In the IM model, RdmLookupValue.Company is paired with Company.IndustryType as a one-to-one: .WithOne("IndustryType").HasForeignKey("Shared.Domain.Models.RdmLookupValue", "CompanyId") (snapshot line 2495). That also puts b.HasIndex("CompanyId").IsUnique() on the entity (line 1676), even though many lookup values share one company. EDM, which owns the table, maps it as HasOne(Company).WithMany().HasForeignKey(CompanyId). There is no DDL impact because the table is excluded from migrations. However, when a tracking query loads several lookup values for the same company (e.g. GRV Types), EF relationship fix-up can re-point Company.IndustryType. Pin it in this configuration: builder.HasOne(lookupValue => lookupValue.Company).WithMany().HasForeignKey(lookupValue => lookupValue.CompanyId);. The F2 attribute approach, applied to Company.IndustryType as well, would also cover it.
