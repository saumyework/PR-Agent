Adds full CRUD for a new BranchMaster entity in the EDM module: endpoints, service, CQRS commands/queries, FluentValidation, and locale strings for two new "in-use" guard messages. It also wires BranchMaster as a dependent of BusinessUnit and Location deletion checks, and adds a small new Location query for address-type lookups. Structure, naming, and CQRS wiring closely follow the existing BusinessUnitService/LocationService patterns.

The core "prevent deleting a branch that's in use" business rule is not actually implemented — the dependency check it relies on is hardcoded to always return false — and the update path throws a misleading "cannot be deleted" message for an unrelated case. Both are in the write path of a new entity and should be fixed before merge.

Errors Warnings Notes Passed

Must-Fix

src/Modules/EnterpriseDataManagement/EnterpriseDataManagement.Application/Services/BranchMasterService.cs:118

Dependency check is a hardcoded stub. HasDependenciesAsync is private static Task<bool> HasDependenciesAsync(Guid id) => Task.FromResult(false); — it never actually queries anything and always returns false. This is used in two places: the DeleteAsync guard (line 81, entity.IsSeeded || entity.IsDeleted || await HasDependenciesAsync(id)) and IsUsedAsync, which backs the /branch-masters/check-if-used/{id} endpoint. As shipped, a branch master can always be deleted regardless of real dependencies, and the "check if used" endpoint will always report false to the frontend. Sibling code in this same PR (LocationService.CheckDependenciesOnDelete, BusinessUnitService.DeleteAsync) does real dependent-record lookups via the repository — this method needs the equivalent real implementation before merge, not a placeholder.

src/Modules/EnterpriseDataManagement/EnterpriseDataManagement.Application/Services/BranchMasterService.cs:65-66

Wrong error message on update. UpdateAsync throws Locale.BranchMasterIsUsed ("This branch cannot be deleted as it has associated transactions.") when entity.IsSeeded is true. That message describes a delete-blocked-by-usage scenario, but this code path is an update being blocked because the record is seed data — an unrelated reason. A user editing a seeded branch will see a confusing, factually wrong error. This needs its own locale key (e.g. something like "seeded/system records cannot be modified") rather than reusing the delete-in-use message.

Suggestions

src/.../BranchMasters/Commands/Create/CreateCommand.cs & Update/UpdateCommand.cs

No server-side uniqueness enforcement. CheckNameExistsAsync/CheckShortCodeExistsAsync are only exposed as separate GET endpoints for the frontend to call before submit; neither CreateCommandValidator nor UpdateCommandValidator enforces uniqueness server-side, so a direct API call bypassing the frontend check can create duplicate branch names/short codes. This mirrors the existing BusinessUnitService pattern (also no server-side uniqueness check), so it's not a regression introduced by this PR, but it's worth tightening here or as a follow-up since it's real write-path validation, not just UX.
