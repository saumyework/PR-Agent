feat(Configuration): Improve query engine [OBPP-12419]

Risk: Medium

This is a large restructuring (~100 files, +8650/-2255) that moves condition/expression evaluation and parameter-resolution logic out of Configuration.Application into a new Kernel module (Kernel.Domain/Kernel.Application/Kernel.Infrastructure), while adding genuinely new functionality: a strategy-pattern operator registry (ConditionOperatorStrategies) shared between an in-memory delegate-compiled evaluator (DelegateExpressionEvaluator) and an EF Core LINQ expression builder (EFCoreExpressionBuilder), plus new diagnostics endpoints under kernel/expressions.

Every file that shows as a plain add/delete pair (rather than a detected rename) was confirmed to be fully migrated with no duplicate/dead code left behind, and test coverage of the new engine is notably strong (concurrency tests, AST guard-rail tests, operator-coverage tests). The one Must-Fix is a silently dropped fallback tier in "$"-variable resolution between the old evaluator and the new one. Overall risk is Medium: the new architecture, caching, and operator design are solid and well tested, but the dropped fallback plus a handful of operand-handling/validation inconsistencies are worth resolving before merge.

Errors Warnings Notes Passed

Must-Fix

src/Modules/Kernel/Kernel.Application/Evaluation/DelegateExpressionEvaluator.cs:283

Dropped fallback tier in "$"-variable resolution. The deleted ConditionEvaluatorService.ResolveSystemContext had a 3-tier fallback for resolving a reference: (1) engine.ResolveParameterSync, (2) look up the variable directly in the runtime context dictionary (the record/entity field values passed into Evaluate) if step 1 returned null, (3) return the raw variable string. The new GetResolvedReferenceValue(Dictionary<string, object?> resolved, string variable) only does resolved.TryGetValue(variable, out var val) ? val : variable, where resolved is populated purely from IParameterResolverEngine.ResolveParameterAsync via ParameterResolverEngineExtensions.ResolveReferencesAsync — the runtime entity context dict is never consulted as a fallback anymore. Any "$"-prefixed reference that used to resolve from the record's own data when the DB-backed parameter resolver returned null will now silently resolve to null instead of its previous value, which can silently change evaluation outcomes for existing conditions built against the old behavior.

Suggestions

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/ConditionOperatorStrategies.cs:135-195

Inconsistent operand-type fallback between comparison and Between. CompareNumeric (backing >, <, >=, <=, line 195) throws NotSupportedException if operands aren't parseable as decimal or DateTime — no string fallback. EvaluateBetween (lines 135-136) has a third fallback tier doing an ordinal string comparison instead of throwing. So name > "abc" throws for a plain string field while name between ["aaa","zzz"] silently succeeds via string comparison on the same field — the two operator families disagree on whether string comparison is valid.

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/ConditionOperatorStrategies.cs:436,451

Divide/modulo-by-zero silently returns 0. r == 0 ? 0.0 : ToDouble(left) / r (and the modulo equivalent) is confirmed intentional via the test Resolve_Divide_ByZero_ReturnsZeroNotException, and mirrored consistently on the EF Core query-build side. It's a documented, tested behavior rather than an oversight, but worth flagging explicitly since it converts a divide-by-zero — often a symptom of bad configuration or missing data — into an indistinguishable valid-looking 0 result rather than a diagnosable error. Please confirm this is the intended product behavior.

src/Modules/Kernel/Kernel.Application/Endpoints/ExpressionDiagnosticsEndpoints.cs:29-38

Two new diagnostics endpoints have no FluentValidation validator. EvaluateExpressionQuery, BatchEvaluateExpressionQuery, and ParseExpressionQuery each have a matching AbstractValidator<>, but ValidateExpressionQuery (POST kernel/expressions/validate) and GetExpressionReferencesQuery (POST kernel/expressions/references) do not. Both degrade gracefully today rather than crashing, but it's inconsistent with the rest of the new surface and with the stack convention of validating every Command/Query at the pipeline boundary.

src/Modules/Kernel/Kernel.Application/UseCases/Fetch/FetchDynamicQuery.cs:48

No upper bound on PageSize. RuleFor(x => x.PageSize).GreaterThan(0) is the only check — a caller can request an arbitrarily large page, and ExecuteQueryAsync<TEntity> passes it straight into Skip/Top against the DB with no cap. This is carried over unchanged from the deleted FetchDynamicQueryHandler.cs (same gap existed before), so it isn't a new regression, but since this PR's stated goal is to improve this exact query path, it's a good opportunity to add a max.

src/Modules/Kernel/Kernel.Application/Evaluation/EFCoreExpressionBuilder.cs:254

Culture-dependent date parsing. DateTime.Parse(sd) here, and the equivalent DateTime.TryParse calls in ConditionOperatorStrategies.cs's AreEqual/CompareNumeric/EvaluateBetween, omit CultureInfo.InvariantCulture. Ambiguous date-literal strings in a stored condition (e.g. "03/04/2026") could parse to a different date depending on the server's OS/culture configuration, producing non-deterministic evaluation results across environments.

Notes

src/Modules/Kernel/Kernel.Application/Evaluation/ExpressionOperatorCache.cs:23-27

Unsynchronized check-then-load on static cache state. The LoadedOperators.Count == 0 || DateTime.UtcNow - LastResetAtUtc > Ttl check plus the subsequent DB load and ResetOperators call isn't guarded by a lock, so concurrent requests hitting an expired/cold cache simultaneously trigger redundant concurrent DB loads. Harmless (last write wins), just wasted work — PerRequestCache.cs in this same PR already demonstrates the Lazy<Task<>> pattern that would fix this cheaply.

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/ConditionOperatorStrategies.cs:211

Reflection lookup for Contains runs on every query build. typeof(Enumerable).GetMethods(...).First(m => m.Name == "Contains" && m.GetParameters().Length == 2).MakeGenericMethod(propType) re-resolves via reflection + LINQ on every in/not_in EF query build, unlike the sibling StringContainsMethod/StringStartsWithMethod/StringEndsWithMethod which are cached as static readonly MethodInfo once. Minor, but an easy consistency fix.

What's Good

src/Web.API.Tests.Integration/Kernel/AstCacheConcurrencyTests.cs

Real concurrency test for the compiled-expression cache. This test evaluates the same cached compiled expression concurrently against 50 different contexts and asserts no cross-contamination — exactly the right test for a static compiled-delegate cache design, and it passes because the compiled delegate only closes over structure, not data.

Shared AST guard rails across both execution backends. ExpressionNodeExtensions.MeasureTree/EnsureWithinLimits (depth/node-count limits) is a single shared extension used by both DelegateExpressionEvaluator and EFCoreExpressionBuilder, with dedicated tests for both thresholds — good protection against pathological/adversarial expression trees implemented once instead of twice.

src/Modules/Kernel/Kernel.Application/ParameterResolution/PerRequestCache.cs

PerRequestCache rewrite fixes a real duplicate-work race. The old implementation did a plain check-then-set against httpContext.Items[key], so two concurrent calls for the same key could both run an expensive/DB-hitting factory. The new version uses ConcurrentDictionary<string, Lazy<Task<object?>>> with LazyThreadSafetyMode.ExecutionAndPublication, guaranteeing the factory runs once per key even under concurrent access.

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/IConditionOperatorStrategy.cs

Clean strategy pattern with a compiler-enforced safety net. Forcing every operator to implement both Evaluate (in-memory) and BuildQueryExpression (EF Core) in one class avoids two independently-maintained switch statements, and the one place this abstraction doesn't reach (the raw-SQL "Dynamic Model" path) is explicitly documented and backed by a coverage test to catch a missing case at test time.
