feat(Configuration): Improve query engine [OBPP-12419]

ososerp #13667 kesharaosos feature/platform/version/0.12.0 ← feature/expression-engine 2026-09-04
Risk: Medium
2Errors 4Warnings 2Notes 5Passed

This is a large architectural extraction: the condition/expression evaluation engine (condition builder, dynamic query fetch, parameter resolution) is pulled out of Configuration.Application into a new standalone Kernel.Application/Kernel.Domain/Kernel.Infrastructure module, and gains a real arithmetic layer (+ - * / % ^) plus a strategy-per-operator design (IConditionOperatorStrategy) shared between the in-memory delegate evaluator and the EF Core query translator. It also turns on a brand-new SQL Server dialect for the raw-SQL "Dynamic Model" query path (only Postgres was wired up before). The old ConditionEvaluatorService (410 lines) and its scattered helper classes are deleted wholesale and replaced by the new engine; the apparent Modules.Domain/Modules.Infrastructure duplication visible in the raw diff is just the old pre-move location being deleted, not leftover dead code. Test coverage is substantial — dozens of new integration test files covering the arithmetic operators, AST serialization/limits, the dialect factory, and the dynamic query builder.

The engine's security posture is solid: the raw-SQL "Dynamic Model" path in DynamicQueryBuilder validates every referenced field name against the model's known columns before generating SQL, uses parameterized values throughout, and both dialects escape LIKE wildcards. Two concrete bugs block merge, though: the value-comparison helpers parse numbers/dates with the ambient thread culture instead of CultureInfo.InvariantCulture, in an app that already switches per-request culture between English and Arabic, so a condition's true/false outcome can depend on the request's language header; and the new SQL Server dialect's In/NotIn filter emits STRING_SPLIT(@p, ',') expecting a comma-delimited string parameter, but the shared ConvertToTypedArray helper that produces the parameter value returns a native .NET array (correct for Postgres's array-native = ANY(@p), not for SqlParameter), so any In/NotIn filter against the newly-enabled SQL Server path will throw at query execution.

Errors Warnings Notes Passed

Must-Fix

src/Modules/Kernel/Kernel.Infrastructure/Services/QueryEngine/DatabaseDialects/SqlServerDialect.cs

SQL Server In/NotIn filters will throw at runtime. SqlServerDialect.BuildFilterCondition generates {column} IN (SELECT value FROM STRING_SPLIT({paramPlaceholder}, ',')) for FilterOperator.In/NotIn, which requires the bound parameter to be a single comma-delimited string. But the value it's bound to comes from DynamicQueryBuilder.BuildSingleFilter → ConvertToTypedArray(filter.Value), which returns a native .NET array (Guid[], int[], string[], ...). That shape is correct for PostgreSqlDialect, whose BuildFilterCondition uses = ANY({paramPlaceholder})/!= ALL({paramPlaceholder}) — Npgsql natively binds arrays as parameter values — but Microsoft.Data.SqlClient's SqlParameter has no array support, and SqlServerDialect.CreateParameter/ConfigureParameter do nothing to convert the array into a delimited string before QueryEngine.ExecuteQueryAsync assigns it to SqlParameter.Value and calls ExecuteReaderAsync. Since SqlServerDialect is new in this PR (previously DatabaseDialectFactory had no working case for it) and is reachable directly from FetchDynamicQuery's "Dynamic Model" fallback, any InList/NotInList condition against a table with no compile-time EF entity will fail the first time it's exercised against a SQL Server-backed deployment. The added SqlServerDialectTests.cs integration tests use EF Core InMemory, which doesn't exercise this ADO.NET parameter-binding path, so this wouldn't have been caught by the new test suite.

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/ConditionOperatorStrategies.cs

Culture-dependent numeric/date evaluation. AreEqual, CompareNumeric, EvaluateBetween, and ToDouble all call decimal.TryParse/double.TryParse/DateTime.TryParse/Convert.ToDouble without CultureInfo.InvariantCulture (same gap in EFCoreExpressionBuilder.ConvertSingle's DateTime.Parse/Convert.ChangeType). Per the C# guide's own DependencyInjection sample, this app's middleware sets up RequestLocalizationOptions with English and Arabic as supported cultures and a per-request culture provider that sets the handling thread's CurrentCulture. Decimal separators and date formats differ across those cultures, so the same stored condition (an automation trigger like amount > 1000, or a new arithmetic expression like price * quantity) can parse and compare differently — or throw where it previously succeeded — purely based on the request's language header. This is new surface area, not just carried-over risk: the arithmetic operators (Add/Subtract/Multiply/Divide/Modulo/Power) are introduced by this PR and route every operand through the same unqualified Convert.ToDouble. Parse with CultureInfo.InvariantCulture everywhere a numeric/date string is round-tripped in this file and in EFCoreExpressionBuilder.ConvertSingle.

Suggestions

src/Modules/Kernel/Kernel.Application/UseCases/Diagnostics/GetExpressionReferencesQuery.cs

Missing validator, unlike its three siblings. EvaluateExpressionQuery, ParseExpressionQuery, and BatchEvaluateExpressionQuery in the same folder all declare an AbstractValidator<T> with at least RuleFor(x => x.Expression).NotNull(). GetExpressionReferencesQuery has no validator, so a request body with a missing/null expression skips straight to parameterResolverEngine.ResolveReferencesAsync(query.Expression, ...), which will throw an unhandled exception (500) instead of the clean 400 its siblings return for the same bad input. Add the matching NotNull() validator for consistency.

src/Modules/Kernel/Kernel.Application/UseCases/Fetch/FetchDynamicQuery.cs

PageSize has no upper bound. FetchDynamicQueryValidator only checks RuleFor(x => x.PageSize).GreaterThan(0) — nothing caps the maximum, so a caller can request an arbitrarily large page against a dynamic-entity Skip/Take query. This PR's own BatchEvaluateExpressionQueryValidator, added in the same change, sets a precedent for exactly this kind of guard (MaxContexts = 100, enforced via LessThanOrEqualTo) — worth applying the same pattern here to protect the fetch endpoint from oversized result sets.

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/ConditionOperatorStrategies.cs

Division/modulo by zero silently returns 0.0. DivideStrategy.Evaluate and ModuloStrategy.Evaluate both return 0.0 when the right operand is zero, which is indistinguishable from a condition that legitimately evaluates to zero (e.g. a / b > 0 silently becomes false instead of surfacing that the rule is undefined for that row). BuildQueryExpression makes the same choice on the EF Core side via Expression.Condition(..., Expression.Default(propertyType), ...), so the two backends are at least consistent with each other — worth confirming this is the intended semantics for automation/approval rules rather than a case that should surface as a diagnostic instead.

src/Modules/Kernel/Kernel.Application/Evaluation/DelegateExpressionEvaluator.cs

Cache config read once per instance, not truly global. maxCacheSize/maxAstDepth/maxAstNodes are instance readonly fields resolved from IConfiguration at construction time (this class is [ScopedService], so re-read every request), while the cache and memberPropertyCache dictionaries backing them are static and shared process-wide. Harmless functionally since these config values don't change per-request, but it's a slightly confusing mix of scoped-read/static-storage — worth a comment, or hoisting the config reads into a singleton options object.

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/ConditionOperatorStrategies.cs

The detailed XML doc explaining that the raw-SQL "Dynamic Model" path has its own independent operator mapping is genuinely useful, but it's on an internal static class so it won't surface in IntelliSense for consumers outside this assembly. Consider moving the "also update the raw-SQL dialect switches" warning onto IConditionOperatorStrategy itself (public-facing to the module), since that's the actionable warning for whoever adds the next operator.

What's Good

src/Modules/Kernel/Kernel.Infrastructure/Services/QueryEngine/QueryBuilder/DynamicQueryBuilder.cs

SQL injection defenses done right for a raw-SQL builder. Every field name that reaches generated SQL — from the condition tree, sort fields, select fields, and filters — is collected up front and checked against the model's real column set via EnsureFieldsAreKnown before any SQL is built, identifiers are quoted through the dialect abstraction rather than string-concatenated, and all values flow through parameterized placeholders (AddParameter). Both dialects' BuildLikePattern also escape %/_/[ wildcards for Contains/StartsWith/EndsWith filters, so user-supplied filter text can't smuggle extra wildcard behavior into a LIKE clause.

src/Modules/Kernel/Kernel.Domain/Extensions/ExpressionNodeExtensions.cs

Resource-exhaustion guard rails applied consistently. EnsureWithinLimits (max AST depth/node count) is called before compiling an expression in both the in-memory delegate evaluator and the EF Core translator, and the regex-based matches operator runs under a 100ms timeout — real ReDoS/resource-exhaustion protection against a client-supplied expression tree, carried through from the code this PR replaces and applied to the new arithmetic surface too.

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/ConditionOperatorStrategies.cs

Clean strategy-per-operator design. Folding "how an operator evaluates in-memory" and "how it translates to an EF Core expression" into one IConditionOperatorStrategy implementation per operator (instead of two parallel switch statements) makes the compiler enforce both code paths exist for any new operator, and the doc comment honestly flags the one place this guarantee doesn't reach (the raw-SQL dialect path), backed by a coverage test (ConditionOperatorKindCoverageTests) that fails at test time instead of first-use-in-prod.

src/Modules/Kernel/Kernel.Application/ParameterResolution/ParameterResolverEngineExtensions.cs

Sync-over-async anti-pattern removed. The deleted ConditionEvaluatorService resolved $-references inside the compiled evaluation lambda via a blocking .GetAwaiter().GetResult() call — exactly the deadlock-prone pattern this codebase's own C# guide calls out. The new ResolveReferencesAsync collects all references up front and awaits them properly before compilation/evaluation runs.

src/Modules/Kernel/Kernel.Application/ParameterResolution/PerRequestCache.cs

Request-cache race condition fixed. The old version's TryGetValue-then-Items[key] = value pattern let two concurrent lookups for the same key both run factory(). The rewrite uses ConcurrentDictionary.GetOrAdd with Lazy<Task<object?>> under ExecutionAndPublication mode, guaranteeing the factory runs exactly once per key even under concurrent access.
