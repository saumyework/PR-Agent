This is a large architectural extraction (183 changed files, +8718/-2272) that moves condition/expression evaluation and parameter-resolution logic out of Configuration.Application into a new standalone Kernel.Domain/Kernel.Application/Kernel.Infrastructure module, adds a real arithmetic layer (+ - * / % ^) via a shared IConditionOperatorStrategy per operator, and turns on a brand-new SQL Server dialect for the raw-SQL "Dynamic Model" query path (previously only Postgres was wired up). The old ConditionEvaluatorService and its scattered helpers are deleted wholesale and replaced end-to-end; test coverage of the new engine is genuinely strong (dozens of new integration test files covering arithmetic, AST serialization/limits, dialects, and the query builder).

This PR has been reviewed twice before (pr13667.html, pr13667-v2.html); this pass re-verified every prior claim against the current branch tip rather than trusting the last review's conclusions. Two results of that: the culture-dependent date/number parsing flagged in earlier passes has since been fixed (all comparison/conversion paths now pass CultureInfo.InvariantCulture explicitly) and is dropped from this review — but a confirmed, still-unresolved SQL Server In/NotIn bug from pr13667-v2.html was silently absent from pr13667-v3.html and is restored here, alongside a new Must-Fix this pass found in the raw-SQL path's AST guard rails. Risk is High: three independent Must-Fix defects each cause a hard runtime failure (an unhandled exception or a broken query) under conditions this PR's own new test suite does not exercise.

Errors Warnings Notes Passed

Must-Fix

src/Modules/Kernel/Kernel.Application/Evaluation/DelegateExpressionEvaluator.cs:275

Dropped fallback tier in "$"-variable resolution. The deleted ConditionEvaluatorService.ResolveSystemContext had a 3-tier fallback: (1) engine.ResolveParameterSync, (2) if that returned null, look the variable up directly in the runtime context dictionary (the record/entity's own field values passed into Evaluate), (3) return the raw variable string. The new GetResolvedReferenceValue(Dictionary<string, object?> resolved, string variable) only does resolved.TryGetValue(variable, out var val) ? val : variable, and resolved is populated purely by ParameterResolverEngineExtensions.ResolveReferencesAsync calling engine.ResolveParameterAsync for each reference — the entity's own context dict is never consulted. Verified against the pre-PR source: any "$"-prefixed reference that used to fall back to the record's own data when the DB-backed resolver returned null will now silently resolve to the literal reference string instead, changing evaluation outcomes for existing stored conditions with no error raised.

src/Modules/Kernel/Kernel.Infrastructure/Services/QueryEngine/DatabaseDialects/SqlServerDialect.cs:263

SQL Server In/NotIn filters will throw at query execution. BuildFilterCondition emits {column} IN (SELECT value FROM STRING_SPLIT({paramPlaceholder}, ',')), which requires the bound parameter to be a single comma-delimited string. The value actually bound to it comes from DynamicQueryBuilder.BuildSingleFilter → ConvertToTypedArray(filter.Value), which returns a native .NET array (Guid[], int[], ...). That shape is correct for PostgreSqlDialect, whose own BuildFilterCondition uses = ANY(@p)/!= ALL(@p) (Npgsql binds arrays natively) — but Microsoft.Data.SqlClient's SqlParameter has no array support, and neither SqlServerDialect.CreateParameter nor ConfigureParameter convert the array into a delimited string first. Since SqlServerDialect is new in this PR (the prior DatabaseDialectFactory had no working SQL Server case at all) and is reachable directly from FetchDynamicQuery's Dynamic Model path, any InList/NotInList filter against a SQL Server-backed deployment fails the first time it runs. Confirmed SqlServerDialectTests.cs in this PR never exercises FilterOperator.In/NotIn, so this wasn't caught.

src/Modules/Kernel/Kernel.Infrastructure/Services/QueryEngine/QueryBuilder/DynamicQueryBuilder.cs:277

AST guard rails and structural validation aren't enforced on the raw-SQL "Dynamic Model" path. ExpressionNodeExtensions.EnsureWithinLimits (max AST depth/node count) and EnsureStructurallyValid are called before DelegateExpressionEvaluator compiles a delegate and before EFCoreExpressionBuilder builds a LINQ expression, but DynamicQueryBuilder.BuildSelectAsync/ValidateAsync — reached via QueryEngine.ExecuteQueryAsync/ValidateQueryAsync from FetchDynamicQuery and ValidateExpressionQuery whenever the target is a Dynamic Model rather than a compile-time EF entity — call neither. This has two concrete consequences: (1) the depth/node-count DoS protection this PR carefully added everywhere else is fully bypassed for Dynamic Model conditions; (2) EnsureStructurallyValid itself has a gap it never gets the chance to hit here — for a BinaryExpressionNode it validates via binary.Right?.EnsureStructurallyValid(...), silently permitting Right == null on a non-nullary operator (e.g. a malformed + or > node). A binary node with a null Right reaches BuildExpressionNodeCondition's default case, which calls node.GetType().Name on that null node — an unhandled NullReferenceException instead of a clean 400. GuardRailsTests.cs only covers DelegateExpressionEvaluator, and DynamicQueryBuilderExpressionNodeTests.cs only tests a null Right for a legitimately-nullary operator, not this case.

Suggestions

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/ConditionOperatorStrategies.cs:170-193

Inconsistent operand-type fallback between comparison and Between. CompareNumeric (backing >, <, >=, <=) throws NotSupportedException when both operands fail to parse as decimal or DateTime — no string fallback. AreEqual and EvaluateBetween both have a third tier that falls back to an ordinal string comparison instead of throwing. So status > "abc" throws for a plain string field while status between ["aaa","zzz"] silently succeeds via string comparison on the same field — the operator families disagree on whether string comparison is valid, and a real string field being sorted/filtered with >/< hits this.

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/ConditionOperatorStrategies.cs:436,451

Divide/modulo-by-zero silently returns 0. DivideStrategy/ModuloStrategy.Evaluate both return 0.0 when the right operand is zero, and BuildQueryExpression makes the identical choice on the EF Core side via Expression.Condition(right == default, default, left/right) — the two backends are at least consistent with each other, and it appears to be a deliberate design choice rather than an oversight. Still worth flagging explicitly: it converts a divide-by-zero — often a symptom of bad configuration or missing data in a formula-driven condition — into an indistinguishable, valid-looking 0 result rather than a diagnosable error. Please confirm this is the intended product semantics for automation/approval rules built on this engine.

Notes

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/ConditionOperatorStrategies.cs:1-30

Doc comment warning about the raw-SQL path lives on an internal class. The XML doc explaining that the Dynamic Model path has its own independent operator mapping that must be kept in sync is genuinely useful, but it's on an internal static class so it won't surface to anyone adding a new operator from outside this file. Consider moving that specific warning onto IConditionOperatorStrategy, the interface every new operator actually implements.

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/ConditionOperatorStrategies.cs:211

Reflection lookup for Contains re-runs on every EF query build. BuildContainsExpression does typeof(Enumerable).GetMethods(...).First(m => m.Name == "Contains" && ...).MakeGenericMethod(propType) fresh each call, unlike the sibling StringContainsMethod/StringStartsWithMethod/StringEndsWithMethod, which are cached as static readonly MethodInfo. Low-impact, but an easy consistency fix — cache per closed generic type in a ConcurrentDictionary<Type, MethodInfo>.

What's Good

src/Modules/Kernel/Kernel.Infrastructure/Services/QueryEngine/QueryBuilder/DynamicQueryBuilder.cs

SQL injection defenses done right for a raw-SQL builder. Every field name reaching generated SQL — from the condition tree, sort fields, select fields, and filters — is collected up front and checked against the model's real column set via EnsureFieldsAreKnown before any SQL is built, identifiers are quoted through the dialect abstraction rather than concatenated, and all values flow through parameterized placeholders. Both dialects' BuildLikePattern also escape %/_/[ wildcards, so filter text can't smuggle extra wildcard behavior into a LIKE clause.

src/Web.API.Tests.Integration/Kernel/AstCacheConcurrencyTests.cs

Real concurrency test for the compiled-expression cache. Evaluates the same cached compiled expression concurrently against many different contexts and asserts no cross-contamination — exactly the right test for a static compiled-delegate cache design, and correct because the compiled delegate closes only over structure, not data.

src/Modules/Kernel/Kernel.Application/ParameterResolution/PerRequestCache.cs

Real duplicate-work race fixed. The old implementation did a plain check-then-set against httpContext.Items[key], so two concurrent calls for the same key could both run an expensive factory. The rewrite uses ConcurrentDictionary<string, Lazy<Task<object?>>> with LazyThreadSafetyMode.ExecutionAndPublication, plus a double-checked lock for store creation, guaranteeing the factory runs exactly once per key under concurrent access.

src/Modules/Kernel/Kernel.Application/Evaluation/Operators/IConditionOperatorStrategy.cs

Clean strategy-per-operator design with a compiler-enforced safety net. Folding "how an operator evaluates in-memory" and "how it translates to an EF Core expression" into one implementation per operator (instead of two parallel switch statements) makes the compiler enforce both paths exist for a new operator, and ConditionOperatorKindCoverageTests backs the one place this guarantee doesn't reach (the raw-SQL dialect switches) with a test that fails at test time instead of first use in production.
