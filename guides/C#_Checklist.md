## Architecture & Structure [Overview]
- Modules are layered into Application, Domain, Infrastructure, Endpoints; keep each layer's responsibility separate [Overview]
- Register all services/repositories via constructor injection in each module's DependencyInjection.cs; never use service locator or static access [Overview]
- Keep command/query handlers single-responsibility; one handler per Command/Query [Overview]
- Define custom exceptions in BuildingBlocks/Exceptions and handle them globally via middleware, not per-endpoint try/catch [Overview]
- Validate every incoming request at the boundary with FluentValidation (via pipeline behavior), not deep inside the handler [Overview]
- Use the generic IRepository<T> for standard data access; use specifications/custom repositories only for complex queries [Overview]
- Never expose domain entities directly in API responses — map to DTOs [Overview]
- Keep endpoint bodies thin; delegate to handlers/services, not inline business logic [Overview]
- Enable nullable reference types in all projects [Overview]
- Prefer records for immutable data (DTOs, Commands, Queries) [Overview]
- Never commit secrets; use environment variables/secret managers in production [Overview]
- Avoid N+1 queries; use projection for large datasets [Overview]

## File Naming [Files]
- File names are PascalCase + .cs (`Student.cs`, `StudentService.cs`), never lowerCamel or snake/underscore [Files]
- Partial-class files use dot-separated PascalCase suffixes (`StudentService.Validations.cs`, `StudentService.Validations.Add.cs`), never concatenated or underscored [Files]

## Variables & Declarations [2.0–2.2]
- Variable names are concise and descriptive of the value's nature; no single-letter or truncated names (`student`, not `s`/`stdnt`), same for lambda parameters [2.0.0]
- Collections are named as plurals, not with a `List`/`Collection` suffix (`students`, not `studentList`) [2.0.1]
- Don't suffix variable names with the type name (`student`, not `studentModel`/`studentObj`) [2.0.2]
- If a variable intentionally stays at its default/null value, the name should say so (`noStudent`, `noChangeCount`) [2.0.3]
- Use `var` only when the right-hand type is obvious from the expression; otherwise declare the explicit type [2.1.0–2.1.1]
- `var` is fine for anonymous types [2.1.2]
- For a single-property object, assign the property directly instead of an object initializer; use an object initializer when there are 2+ properties [2.1.3]
- Break variable declarations that exceed 120 characters at the `=` sign [2.2.0]
- Multi-line declarations get a blank line before and after; single-line declarations are not separated by blank lines [2.2.1]

## Classes & Fields [3.0–3.2]
- Model classes are named after the entity, no `Model` suffix (`Student`, not `StudentModel`) [3.0.0]
- Service classes are singular and suffixed `Service` (`StudentService`), never plural, `BusinessLogic`, or `BL` [3.0.1]
- Class fields are camelCase, no `_` prefix and no PascalCase [3.1.0]
- Reference private fields with `this.`, don't use an underscore-prefixed field name instead [3.1.1]
- When calling a constructor, use named arguments unless the local variable names already match the parameter names; don't use bare `new(...)` target-typed calls for multi-arg constructors [3.2.0]
- When initializing an object, assign properties/constructor args in the same order they're declared in the class [3.2.1]

## Endpoints & Routes [5.0–5.3]
- Endpoint-grouping static methods follow `Map` + ModuleName + `Endpoints` (`MapStudentEndpoints`), not `MapCrudStudentEndpoints` [5.0.0]
- Route segments are camelCase plural nouns; the HTTP verb conveys the action, don't put verbs in the path (`students`, not `Students` or `/createStudents`) [5.1.1]
- When looking up by a non-primary-key property, include that property name in the route (`/courseId/{id}`), don't use `GetById/{id}` or bare `id/{id}` [5.1.2]
- Command/Query class names follow `[action prefix][ModuleNamePlural][Query|Command]` (`GetStudentsQuery`, `CreateStudentCommand`, `DeleteStudentCommand`) — not `GetStudent` or `StudentCommand` [5.2]
- Query handlers must be read-only (no state mutation); Command handlers perform the write and may include validation/logging/events [5.2.2–5.2.3]
- Commands implementing `ICommand<TResponse>` need a matching FluentValidation `AbstractValidator` — `CommandValidationBehavior` runs it automatically and throws before the handler executes [5.2.3.2, 6.2.6]
- Register each module's `MapEndpoints` call inside that module's own DependencyInjection.cs, never in Program.cs [5.3]

## Auth, Middleware & MediatR Pipeline [6.0–6.2]
- Authentication/authorization go through `app.UseAuthentication()` / `app.UseAuthorization()` middleware, not ad hoc checks [6.0]
- Respect the fixed middleware order: RequestLocalization → Swagger(dev) → buffering → PathBase → CORS → Authentication → Authorization → Endpoints → ExceptionHandler → HangfireDashboard [6.1.1]
- Module endpoint registration in Program.cs follows `app.Use` + ModuleName + `Endpoints` (`app.UseDmsEndpoints()`), not `UseDmsModuleEndpoints()` [6.1.2]
- Queries implementing `IQuery<TResponse>` also need a validator — `QueryValidationBehavior` enforces it the same way as commands [6.2.8]
- Don't rely on `ApiKeyBehavior`/manual API-key checks alone for protecting a new endpoint — confirm the endpoint is covered by `AuthorizationBehavior` or has `[AllowAnonymous]` deliberately [6.2.2–6.2.3]
- Any exception constructed for a failure must actually be thrown, not just instantiated and discarded [6.2.2.2]
- New response DTOs with a `HasPendingDocTypeApproval`-style workflow flag must be a writable property for `WorkflowApprovalBehavior` to populate it [6.2.9]

## Naming & Readability [CodeStructure]
- PascalCase for files/classes, camelCase for locals/params/private fields; avoid vague suffixes like `Helper`, `BL`, `Utils` [CodeStructure]
- Endpoint grouping methods follow `Map` + ModuleName + `Endpoints` [CodeStructure]
- Break lines over 120 characters; indent blocks/initializers/nested calls; separate logical sections with blank lines [CodeStructure]
- Comments should explain non-obvious intent only; delete redundant, outdated, or misleading comments instead of relying on them to explain unclear code [CodeStructure]
- Follow standard .NET naming/style conventions; use FluentValidation for all validation; organize by feature/layer [CodeStructure]

## .NET/Language Specifics [DotNet]
- Register dependencies via `services.Add{Scoped|Singleton|Transient}<I,T>()`; never `new` up a dependency inside a class that should receive it via DI [DotNet]
- Handlers and I/O-bound calls must be `async`/`await` end-to-end; never call `.Result` or `.Wait()` on a Task (deadlock risk) [DotNet]
- Use `?` for nullable reference types and handle null explicitly; avoid `!` (null-forgiving) unless truly certain [DotNet]
- Split large classes into partial-class files by concern (validation, exceptions, persistence) rather than one large file [DotNet]

## Business Logic / CQRS Discipline [Functionality, Maintainability]
- Don't mix read and write logic in the same class/handler (no `StudentManager` with both `CreateStudent` and `GetStudent`) [Functionality]
- Don't hardcode business rules in endpoints/controllers (e.g. inline `if (user.Age < 18)`); push rules into domain/service layer [Functionality]
- Avoid deeply nested conditionals; avoid magic strings/numbers for status/flag comparisons [Functionality]
- Custom exception messages must be specific and informative, not generic placeholder text [Functionality]
- Don't hardcode environment checks (`Environment.GetEnvironmentVariable("ENV") == "qa-uat"`); drive behavior from configuration [Functionality]
- Don't register endpoints or services directly in Program.cs; use each module's DependencyInjection.cs [Maintainability]
- Don't create two services for the same purpose; extract shared logic instead of duplicating it (DRY) [Maintainability]
- Apply SOLID: no God classes mixing persistence/logging/validation; extend via new implementations rather than editing existing branches (OCP); don't build fat interfaces forcing unused method implementations (ISP); high-level code depends on abstractions, not `new ConcreteClass()` (DIP) [Maintainability]
- Controllers/endpoints must not contain business logic (if/else chains, DB access, domain rules) — only send to MediatR and return the result [Maintainability]
- Don't use MediatR just to call a single service with no cross-cutting need — that's unnecessary indirection [Maintainability]
- Don't let a handler do too much (validate + log + audit + update + email); split into services [Maintainability]
- Never skip validation on a Command/Query — pair every one with a FluentValidation validator [Maintainability]

## Exceptions & Logging [ErrorHandling]
- Throw domain/module-specific exceptions (e.g. `RecruitmentDomainException`), not bare `throw new Exception(...)` [ErrorHandling]
- Don't silently swallow failures (`return default;`) — surface via exception or explicit error result [ErrorHandling]
- Reuse existing exception types for consistent API error responses: `BadRequestException`, `CompanyCountMissMatchException`, `CustomValidationException`, `DomainException`, `ForbiddenException`, `InternalServerException`, `LicenseValidationException`, `NotFoundDictionaryItemException`, `NotFoundException`, `UserLimitExceedException`, `UserRoleExistsException` [ErrorHandling]
- Never log passwords, tokens, API keys, or full JWTs; mask/redact sensitive fields [ErrorHandling]
- Use structured, meaningful log entries with appropriate log levels, not generic unstructured messages [ErrorHandling]

## Security [Security]
- All input validated via FluentValidation to block injection/bad data [Security]
- Build queries with LINQ/EF (parameterized) — never string-concatenate values into `FromSqlRaw`/dynamic LINQ expressions [Security]
- Secrets live in user-secrets/secret manager or Keycloak, never hardcoded in source [Security]
- Every request path must go through the standard authentication/authorization behaviors — don't bypass with a custom shortcut [Security]

## Performance [Performance]
- Select only needed columns/fields; don't pull entire entities when a projection suffices [Performance]
- Use bulk operations (`AddRangeAsync`/`RemoveRange`) instead of looping single `Add`/`SaveChangesAsync` calls per entity [Performance]
- Don't call `SaveChangesAsync` or issue a DB/API call inside a loop, once per item — batch it [Performance]
- Return paginated results for list endpoints; don't return full unbounded lists [Performance]
- Handlers awaiting I/O must be truly async; don't block with `.Result` [Performance]

## Database Transactions [DbTransactions]
- Wrap multi-step related DB writes in an explicit transaction (`BeginTransactionAsync`); commit only after every operation succeeds [DbTransactions]
- Every transaction's `catch` block must call `RollbackAsync()` — never swallow the exception or log-only without rolling back [DbTransactions]
- Never commit before all operations in the logical unit are complete; don't commit partway through and continue writing [DbTransactions]
- Keep transaction scope short — don't perform external/non-DB calls (HTTP, email) inside the transaction boundary [DbTransactions]
- Don't open nested/unrelated transactions or mix multiple `DbContext`s in one transaction without coordinating them [DbTransactions]
- Prefer Unit-of-Work / single `SaveChangesAsync` per logical operation over multiple independent `SaveChangesAsync` calls that can partially fail [DbTransactions]

## Validation [Testing]
- Every Command and Query needs a matching `AbstractValidator<T>` — this is enforced by `CommandValidationBehavior`/`QueryValidationBehavior` at runtime, but must exist at the PR level [Testing]
- Don't accept and use unvalidated input directly in a handler [Testing]

## Version Control & PR Hygiene [VersionControl]
- One logical change per commit; don't mix UI, logic, and DB changes in a single commit [VersionControl]
- Commit subject in imperative mood, ~50 chars, with issue reference/body when needed; avoid "WIP"/"Fix bug"/"Updates" [VersionControl]
- No debug/temporary code (`var_dump`, stray `console.log`-equivalents, leftover TODOs meant to be resolved) left in the diff [VersionControl]
- PR is scoped to one feature/fix, linked to a tracked item, with a clear (non-vague) title and description [VersionControl]
