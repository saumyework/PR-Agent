>Files

The following are the naming conventions and guidance for naming C# files.

Naming
File names should follow the PascalCase convention followed by the file extension .cs.

Do


Student.cs
Also, Do


StudentService.cs
Don't


student.cs
Also, Don't


studentService.cs
Also, Don't


Student_Service.cs
Partial Class Files
Partial class files are files that contain nested classes for a root file. For instance:

StudentService.cs

StudentService.Validations.cs

StudentService.Exceptions.cs

Both validations and exceptions are partial classes to display a different aspect of any given class in a multi-dimensional space.

Do


StudentService.Validations.cs
Also, Do


StudentService.Validations.Add.cs
Don't


StudentServiceValidations.cs
Also, Don't


StudentService_Validations.cs


> Variables

2.0 Naming
Variable names should be concise and representative of nature and the quantity of the value it holds or will potentially hold.

2.0.0 Names
Do


var student = new Student();
Don't


var s = new Student();
Also, Don't


var stdnt = new Student();
The same rule applies to lambda expressions:

Do


students.Where(student => student ... );
Don't


students.Where(s => s ... );
 

2.0.1 Plurals
Do


var students = new List<Student>();
Don't


var studentList = new List<Student>();
 

2.0.2 Names with Types
Do


var student = new Student();
Don't


var studentModel = new Student();
Also, Don't


var studentObj = new Student();
 

2.0.3 Nulls or Defaults
If a variable value is it's default such as 0 for int or null for strings and you are not planning on changing that value (for testing purposes for instance) then the name should identify that value.

Do


Student noStudent = null;
Don't


Student student = null;
Also, Do


int noChangeCount = 0;
But, Don't


int changeCount = 0;
 

2.1 Declarations
Declaring a variable and instantiating it should indicate the immediate type of the variable, even if the value is to be determined later.

2.1.0 Clear Types
If the right side type is clear, then use var to declare your variable

Do


var student = new Student();
Don't


Student student = new Student();
 

2.1.1 Semi-Clear Types
If the right side isn't clear (but known) of the returned value type, then you must explicitly declare your variable with it's type.

Do


Student student = GetStudent();
Don't


var student = GetStudent();
 

2.1.2 Unclear Types
If the right side isn't clear and unknown (such as an anonymous types) of the returned value type, you may use var as your variable type.

Do


var student = new
{
    Name = "Hassan",
    Score = 100
};
 

2.1.3 Single-Property Types
Assign properties directly if you are declaring a type with one property.

Do


var inputStudentEvent = new StudentEvent();
inputStudentEvent.Student = inputProcessedStudent;
Don't


var inputStudentEvent = new StudentEvent
{
    Student = inputProcessedStudent
};
Also, Do


var studentEvent = new StudentEvent
{
    Student = someStudent,
    Date = someDate
}
Don't


var studentEvent = new StudentEvent();
studentEvent.Student = someStudent;
studentEvent.Date = someDate;
2.2 Organization
2.2.0 Breakdown
If a variable declaration exceeds 120 characters, break it down starting from the equal sign.

Do


List<Student> washingtonSchoolsStudentsWithGrades = 
    await GetAllWashingtonSchoolsStudentsWithTheirGradesAsync();
Don't


List<Student> washgintonSchoolsStudentsWithGrades = await GetAllWashingtonSchoolsStudentsWithTheirGradesAsync();
 

2.2.1 Multiple Declarations
Declarations that occupy two lines or more should have a new line before and after them to separate them from previous and next variables declarations.

Do


Student student = GetStudent();
List<Student> washingtonSchoolsStudentsWithGrades = 
    await GetAllWashingtonSchoolsStudentsWithTheirGradesAsync();
School school = await GetSchoolAsync();
Don't


Student student = GetStudent();
List<Student> washgintonSchoolsStudentsWithGrades = 
    await GetAllWashingtonSchoolsStudentsWithTheirGradesAsync();
School school = await GetSchoolAsync();
Also, declarations of variables that are of only one line should have no new lines between them.

Do


Student student = GetStudent();
School school = await GetSchoolAsync();
Don't


Student student = GetStudent();
School school = await GetSchoolAsync();

>Classes

3.0. Naming
Classes that represent services or brokers in a Standard-Compliant architecture should represent the type of class in their naming convention, however that doesn't apply to models.

3.0.0 Models
Do


class Student {
	...
}
Don't


class StudentModel {
}
 

3.0.1 Services
In a singular fashion, for any class that contains business logic.

Do


class StudentService {
	....
}
Don't


class StudentsService{
	...
}
Also, Don't


class StudentBusinessLogic {
	...
}
Also, Don't


class StudentBL {
	...
}
3.1 Fields
A field is a variable of any type that is declared directly in a class or struct. Fields are members of their containing type.

3.1.0 Naming
Class fields are named in a camel cased fashion.

Do


class StudentsController {
	private readonly string studentName;
}
Don't


class StudentController {
	private readonly string StudentName;
}
Also, Don't


class StudentController {
	private readonly string _studentName;
}
Should follow the same rules for naming as mentioned in the Variables sections.

 

3.1.1 Referencing
When referencing a class private field, use this keyword to distinguish private class member from a scoped method or constructor level variable.

Do


class StudentsController {
	private readonly string studentName;
	public StudentsController(string studentName) {
		this.studentName = studentName;
	}
}
Don't


class StudentController {
	private readonly string _studentName;
	public StudentsController(string studentName) {
		_studentName = studentName;
	}
}
 

3.2 Instantiations
3.2.0 Input Params Aliases
If the input variables names match to input aliases, then use them, otherwise you must use the aliases, especially with values passed in.

Do


int score = 150;
string name = "Josh";
var student = new Student(name, score);
Also, Do


var student = new Student(name: "Josh", score: 150);
But, Don't


var student = new Student("Josh", 150);
Also, Don't


Student student = new (...);
3.2.1 Honoring Property Order
When instantiating a class instance - make sure that your property assignment matches the properties order in the class declarations.

Do


public class Student
{
	public Guid Id {get; set;}
	public string Name {get; set;}
}
var student = new Student
{
	Id = Guid.NewGuid(),
	Name = "Elbek"
}
Also, Do


public class Student
{
	private readonly Guid id;
	private readonly string name;
	public Student(Guid id, string name)
	{
		this.id = id;
		this.name = name;
	}
}
var student = new Student (id: Guid.NewGuid(), name: "Elbek");
Don't


public class Student
{
	public Guid Id {get; set;}
	public string Name {get; set;}
}
var student = new Student
{
	Name = "Elbek",
	Id = Guid.NewGuid()
}
Also, Don't


public class Student
{
	private readonly Guid id;
	private readonly string name;
	public Student(string name, Guid id)
	{
		this.id = id;
		this.name = name;
	}
}
var student = new Student (id: Guid.NewGuid(), name: "Elbek");
Also, Don't


public class Student
{
	private readonly Guid id;
	private readonly string name;
	public Student(Guid id, string name)
	{
		this.id = id;
		this.name = name;
	}
}
var student = new Student (name: "Elbek", id: Guid.NewGuid());

> Endpoints
5.0 Static Method Naming
The static method used to group relevant endpoints should clearly relate to the module it handles.

5.0.0 Naming Convention: Prefix, Module, and Postfix
Static method names must:

Begin with the prefix Map.

Follow with the relevant module name.

End with the postfix Endpoints.

Do


public static void MapStudentEndpoints(this WebApplication app) 
{ 
    ...
}
Don’t


public static void MapCrudStudentEndpoints(this WebApplication app) 
{ 
    ...
}
 

5.1 Endpoint URL Paths
Each endpoint should clearly indicate the module it pertains to through the URL path.

5.1.1 Route Segments for Common URL Paths
Endpoints should convey the action being performed through the HTTP method itself (GET, POST, PUT, DELETE), so there is no need to include the action name in the route segment. Use camelCase plural naming for route segments.

Do


public static void MapStudentEndpoints(this WebApplication app)
{
    var group = app.MapGroup("students");
    group.MapPost("/", async (Stage request, ISender sender) => { });
}
Don’t


public static void MapStudentEndpoints(this WebApplication app)
{
    var group = app.MapGroup("Students");
    group.MapPost("/", async (Stage request, ISender sender) => { });
}
Don’t


public static void MapStudentEndpoints(this WebApplication app)
{
    var group = app.MapGroup("students");
    group.MapPost("/createStudents", async (Stage request, ISender sender) => { });
}
 

5.1.2 Route Segments for Special Cases
When retrieving data using a property other than the primary key, the property name should be included in the route segment to clearly indicate the intent.

For example, if Id is the primary key and courseId is an alternate property:

Do


group.MapGet("/{id}", async (Stage request, ISender sender) => { });
Also, Do


group.MapGet("/courseId/{id}", async (Stage request, ISender sender) => { });
Don’t


group.MapGet("id/{id}", async (Stage request, ISender sender) => { });
Don’t


group.MapGet("GetById/{id}", async (Stage request, ISender sender) => { });
Don’t


group.MapGet("/getByCourseId/{id}", async (Stage request, ISender sender) => { });
 

5.2 Query/Command Naming
Every Query or Command class should clearly communicate its purpose. The name should follow this pattern:



[action prefix] + [module name in plural] + [Query/Command postfix]
Do


GetStudentsQuery
CreateStudentCommand
DeleteStudentCommand
Don’t


GetStudent
StudentCommand
5.2.1 Handlers for queries/commands
In CQRS (Command Query Responsibility Segregation), the Handle method is a core component used in both Queries and Commands, typically in combination with the Mediator pattern via MediatR in .NET.

5.2.2 Handler in Query
Handlers in Queries use for data retrievals.

5.2.2.1 Purpose
To fetch data (read-only operation).

Returns some result without modifying state.

5.2.2.1 Usage
Implements the logic for retrieving the requested data.

Uses services to gather and return data.

Most of the times these queries will return pagination results as the response.

5.2.2.1 Example


public async Task<UserDto> Handle(GetUserByIdQuery request, CancellationToken cancellationToken)
{
    var result = await userService.GetByIdAsync(request.Id);
    return new(user);
}
5.2.3 Handler in Command
Handlers in commands use for data write operations.

5.2.3.1 Purpose
To perform an action that modifies the state of the system (create/update/delete).

Might return a result, but main goal is side effects.

5.2.3.1 Usage
Implements the business logic to change the system state.

May include validation, logging, events etc.

5.2.3.1 Example


public async Task<Guid> Handle(CreateUserCommand request, CancellationToken cancellationToken)
{
    var user = new User { Name = request.Name, Email = request.Email };
    await userService.AddAsync(user);
    return new CreateUserResult(user);
}
5.2.3.2 Fluent Validation Example


public record CreateUserCommand(CreateUserDto User) : ICommand<CreateUserResult>;
public record CreateUserResult(User User);
public class CreateUserValidator : AbstractValidator<CreateUserCommand>
{
    public CreateUserValidator()
    {
        RuleFor(p => p.User.Code).NotNull().WithMessage("CodeIsRequired");
        RuleFor(p => p.User.Title).NotNull().WithMessage("TitleIsRequired");
    }
}

Each MapEndpoints method should be registered inside the module’s own DependencyInjection.cs file, not in Program.cs. This keeps the application modular and the main file clean and organized.

6.1 Middleware Pipeline
In the application we use a middleware pipeline that processes each HTTP request. The pipeline is configured by calling app.Use...() methods in order. 

6.1.1 Pipeline order
Following chart will show the order of the pipeline in our application.

Order

Middleware

Description

1

app.UseRequestLocalization();

Sets the culture for each request based on headers or query parameters.

2

app.UseSwagger(); (dev only)

Enables Swagger UI for API testing.

3

app.Use(async (context, next) => { context.Request.EnableBuffering(); await next(); });

Allows reading the request body multiple times (useful for logging).

4

5

Authenticates requests.

7

app.UseAuthorization();

6.2 MediatR Pipeline Behaviors
After middleware completes and the request reaches a handler (via MediatR.Send()), the pipeline behaviors are executed in sequence before the actual request handler runs. These behaviors encapsulate cross-cutting concerns.

6.2.1 Steps of Authentication and Authorization Behaviors overview
The following behaviors are applied in the order they are registered in the DI container.

Step

Behavior

Purpose

Middleware Authentication

Authorization: Bearer ...

JWT token validated, user claims set in HttpContext.

MediatR Pipeline Behavior #1

AuthKey header (optional)

Custom auth key decrypted and user claims set if present.

MediatR Pipeline Behavior #2

-

Authorization enforced based on user claims and request.

These are executed for every IRequest<TResponse> using MediatR. For example:



await mediator.Send(new CreateStudentCommand(...));
This way, the system supports two authentication approaches seamlessly:

Standard Bearer JWT token authentication.

Custom AuthKey header for special scenarios.

 

6.2.2 API Key Behavior
This MediatR pipeline behavior enforces API key-based validation for incoming requests. It's typically used to protect APIs from unauthorized access.

6.2.2.1 When It's Used
This behavior is injected into the MediatR pipeline and runs before the actual request handler. If an API key is missing or incorrect, it triggers an authorization failure. 

6.2.2.2 How It Works


internal class ApiKeyBehavior<TRequest, TResponse>(
    IHttpContextAccessor httpContextAccessor,
    IConfiguration configuration)
IHttpContextAccessor — gives access to the current HTTP context (so you can read headers).

IConfiguration — lets you read your configured API key from appsettings.json or environment variables.



public async Task<TResponse> Handle(...)
This is where the actual logic happens.



var httpContext = httpContextAccessor.HttpContext;
Ensures that the request is part of an HTTP pipeline (e.g., not a background task).



httpContext.Request.Headers.TryGetValue(ApiKeyIdentifiers.TenantBasedApiKey, out var extractedApiKey)
Looks for the specific header sent by the client. The header key is stored in a constant (ApiKeyIdentifiers.TenantBasedApiKey).



var apiKey = configuration.GetValue<string>(ApiKeyIdentifiers.TenantBasedApiKey);
if (apiKey is not null && apiKey.Equals(extractedApiKey))
{
    httpContext.Items[ContextItemsKeys.ApiKeyValid] = true;
}
else
{
    new BehaviorExceptions("You are not authorized to access this resource.");
}
Retrieves the expected API key from configuration.

If the keys match, it stores a flag ApiKeyValid = true in the HTTP context so downstream components (maybe policies or filters) can check it.

If they don’t match, it tries to create an exception — but doesn't throw it (this is a bug, see below).



return await next();
If no issue is found, execution continues to the next behavior or the handler itself.

 

6.2.3 Authorization Behavior
6.2.3.1 Purpose
It's a way to centralize and enforce fine-grained access control for each request without scattering Authorize attributes across your codebase.

6.2.3.2 How It Works


internal class AuthorizationBehavior<TRequest, TResponse>(...)
Injects:

IHttpContextAccessor – access to current HTTP request

IAuthService – your domain-level service for user-role checks

IConfiguration – access environment values, API keys, etc.



SetGrantsBasedOnRequestName(requestName);
This method inspects the TRequest type's name and infers the required permissions



if (configuration[ConfigurationProperties.Environment] == ConfigurationProperties.Testing)
Allows skipping access checks if you're in testing mode (good for integration tests).



if (endpoint?.Metadata.GetMetadata<AllowAnonymousAttribute>() is not null && menuId == DefaultValues.Default.ToLower())
If:

Endpoint allows anonymous access

MenuId header is set to a default value (likely a placeholder)

Then → skips authorization.



await AuthorizedRequestAsync(httpContext);
This is the heart of the behavior. It:

Checks for a MenuId header → if found, treats as user-based request and checks roles

If no MenuId, looks for X-Api-Key → treats as API key-based request

If neither → considers request unauthorized



await AuthorizeUserAsync(httpContext, headerValue);
await authService.IsUserAuthorized(menuId, grants);
Which checks:

Does the current user (from HttpContext) have the required grants for the menu/module?



await AuthorizeApiKeyAsync(httpContext, extractedApiKey);
Compares the X-Api-Key value to what's configured

If matches → assumes full access (Grants.Add(ModuleRoleGrants.All))



public enum ModuleRoleGrants

6.2.4 Auth Key Behavior
The AuthKeyBehavior<TRequest, TResponse> is a MediatR pipeline behavior that handles authentication based on a custom AuthKey header. It ensures that, if present, a token is validated and the corresponding user info is attached to the HttpContext.User

6.2.4.1 Purpose
To authenticate a request using a custom token (not JWT, but likely something like a proprietary API token or access key), and populate the HTTP context with user information if the token is valid.

6.2.4.2 How It Works


var httpContext = httpContextAccessor.HttpContext;
Gets the HTTP request context for the current request.



httpContext.Request.Headers.TryGetValue(KeyNames.AuthKey, out StringValues token)
From here the AuthKey header will be extracted.



var userAuthKeyRequest = authKeyService.DecryptProcessAccessToken(token);
This method likely:

Decrypts the token.

Parses it into a model (e.g., containing userId, email, etc.)

Validates its structure or expiration.



TokenDto? tokenDto = userAuthKeyRequest is not null
    ? await authKeyService.AuthUserAsync(userAuthKeyRequest)
    : null;
If the token was successfully decrypted, it tries to authenticate the user.

AuthUserAsync checks if the user is known and active.



var claims = new List<Claim>
{
    new Claim(ClaimName.UserId, tokenDto.User.Id.ToString()),
    new Claim(ClaimTypes.Email, tokenDto.User.Email)
};
var identity = new ClaimsIdentity(claims, "CustomAuth");
httpContext.User = new ClaimsPrincipal(identity);
If the token is valid and the user exists:

A list of claims (like user ID and email) is created.

These are added to a custom ClaimsIdentity.

This identity is then assigned to httpContext.User, allowing downstream code (e.g., controllers, services, or authorization filters) to know who the user is.



await next();
If the token is missing or invalid, the request just continues.

6.2.4.3 How It's Registered
In relevant module DependencyInjection.cs file setup:



config.AddOpenBehavior(typeof(AuthKeyBehavior<,>));
 

6.2.5 Doc Naming Behavior
The DocNamingBehavior<TRequest, TResponse> is a custom MediatR pipeline behavior that dynamically applies document auto-naming logic to incoming POST requests based on headers like DocumentTypeCode and CompanyCode.

6.2.5.1 Purpose
This behavior intercepts requests and:

Checks if a document type code is present.

Applies automatic naming (e.g., serial number generation or prefixing).

Mutates the request body before it reaches the handler.

Updates the serial number once the request is processed.

6.2.5.2 How It Works


if (context.Request.Method.Equals(HTTPMethods.Post, ...))
Only applies this logic to POST requests, since auto-naming typically occurs during creation.



context.Request.Headers.TryGetValue(KeyNames.DocumentTypeCode, out ...)
Looks for headers like: 

DocumentTypeCode: INV001 CompanyCode: OS123 

If either is missing or DocumentTypeCode is "DEFAULT" (likely a constant to skip naming), then the behavior exits early.



requestBody = ExtractRequestBody(request);
This reflects into the request object to get the payload and serializes it to a JSON string.



if (string.IsNullOrEmpty(requestBody) || !IsJsonObject(requestBody))
If the extracted JSON is not valid or not an object ({}), it exits early.

6.2.6 Command Validation Behavior
The CommandValidationBehavior<TRequest, TResponse> that you're using is a custom MediatR pipeline behavior designed to validate command requests before they are handled by their respective handlers. This pattern is a clean way to apply cross-cutting concerns such as validation, logging, or authorization. This is located under the BuildingBlocks behaviors.

6.2.6.1 Purpose
It ensures that commands (requests implementing ICommand<TResponse>) are validated using FluentValidation validators before being executed by their handler.

6.2.6.2 How It Works


public class CommandValidationBehavior<TRequest, TResponse>
    (IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : ICommand<TResponse>
IPipelineBehavior<TRequest, TResponse>: Part of MediatR, allows you to intercept the handling of requests.

IEnumerable<IValidator<TRequest>> validators: All FluentValidation validators that apply to this specific command (TRequest) are injected.



var context = new ValidationContext<TRequest>(request);
Creates a FluentValidation context using the incoming command.



var validationResults = await Task.WhenAll(validators.Select(v => v.ValidateAsync(context, cancellationToken)));
Runs all applicable validators asynchronously.



var failures = validationResults
    .Where(r => r.Errors.Any())
    .SelectMany(r => r.Errors)
    .ToList();
Collects all validation failures.



if (failures.Any())
    throw new ValidationException(failures);
If any validation errors exist, it throws a FluentValidation.ValidationException. This prevents the command handler from running.



return await next();
If validation passes, the command proceeds to the next behavior or handler.

In relevant module DependencyInjection.cs file setup:

This tells MediatR to automatically insert this behavior for any command implementing ICommand<TResponse>, assuming matching validators are registered via:

Suppose you have a command like:

private static Expression ConvertToTypeExpression(Type type, string value)
{
    Type underlyingType = Nullable.GetUnderlyingType(type) ?? type;
    object typedValue = value;
    if (underlyingType.IsEnum && Enum.TryParse(underlyingType, value, true, out var enumValue))
    {
        typedValue = enumValue;
    }
    else if (underlyingType == typeof(DateTime) && DateTime.TryParse(value, out var dt))
    {
        typedValue = dt;
    }
    else
    {
        try
        {
            typedValue = Convert.ChangeType(value, underlyingType);
        }
        catch
        {
            return Expression.Constant(null, type);
        }
    }
    return Expression.Constant(typedValue, type);
}

The LoggingBehavior<TRequest, TResponse> is a MediatR pipeline behavior that captures and logs details about non-GET HTTP requests and their responses. It's primarily used for auditing and tracking user actions, particularly for write or update operations (e.g., POST, PUT, DELETE).

How It Works


public async Task<TResponse> Handle(...)
Executes before and after a MediatR request.

Proceeds to the next() delegate to execute the actual handler.

After the handler runs, it:

Reads the HTTP request body (unless it's GET).

Serializes and processes the response.

Constructs a log entry with user details and request/response info.

Outputs the audit log to the console (could be extended to file/DB/etc)



ReadRequestBody(HttpRequest request)
Reads and returns the raw body content of the request.

Supports both JSON and multipart/form-data (like file uploads).

Uses request.EnableBuffering() to allow multiple reads of the body stream.



CreateAuditLog(HttpContext context, string requestBody, string responseBody)
Builds an anonymous object that captures:

Status code, method (GET/POST/PUT...)

User identity (ID, email, full name, etc.)

Request and response bodies

Uses ClaimTypes and custom claim names to fetch user info.

Serializes it to JSON and logs to console using:

  "data": { ...audit log info... }

RemoveWrapperObject(string json)

> Database Transaction Handling

When performing multiple related database operations, ensuring consistency is crucial. Transactions help maintain data integrity — especially when multiple changes need to succeed or fail as a group.

ACID properties
Property

Description

Why It Matters

A – Atomicity

All operations in a transaction succeed or none do.

Prevents partial updates (e.g., debiting account without crediting the other).

C – Consistency

Transactions move the DB from one valid state to another.

Business rules stay intact (e.g., referential integrity).

I – Isolation

Transactions don’t interfere with each other.

Prevents dirty reads, lost updates, etc.

D – Durability

Once committed, changes survive crashes.

Data stays safe after success.

Transactions are used when multiple DB operations must succeed together
Do:

Group related DB operations that must succeed or fail together (e.g., updating multiple tables).

Begin a transaction explicitly when you have multiple dependent operations.

Commit the transaction only after all operations succeed.

Rollback the transaction immediately if any operation fails or throws an exception.

Use async/await for async database calls inside transactions.

Use appropriate isolation levels to balance data consistency and concurrency performance.

Use Unit of Work or DbContext as a transaction boundary.

Keep the transaction scope as short as possible to reduce locking and improve performance.

Use try/catch blocks to ensure rollback on errors.

Use transactional retries or circuit breakers if transient failures occur.

Log transaction start, commit, and rollback for troubleshooting.



public async Task AddWithTransactionAsync(List<T> entities)
{
    using var transaction = await dbContext.Database.BeginTransactionAsync();
    try
    {
        await dbContext.Set<T>().AddRangeAsync(entities);
        await dbContext.SaveChangesAsync();
        // Commit only after all operations succeed
        await transaction.CommitAsync();
    }
    catch (Exception ex)
    {
        // Rollback on any failure
        await transaction.RollbackAsync();
        throw new InfrastructureException($"Transaction failed: {ex.Message}");
    }
}
public async Task AddEntitiesAsync(List<T> entities)
{
    using var transaction = await dbContext.Database.BeginTransactionAsync();
    try
    {
        await dbContext.Set<T>().AddRangeAsync(entities);
        await dbContext.SaveChangesAsync();
        await transaction.CommitAsync();
    }
    catch
    {
        await transaction.RollbackAsync();
        throw;
    }
}
// Call external services separately after committing
public async Task ProcessDataAsync(List<T> entities)
{
    await AddEntitiesAsync(entities);
    await SomeExternalCallAsync();
}
Don’t:

Don’t perform unrelated operations in the same transaction.

Don’t commit a transaction before all work is complete.

Don’t leave transactions open for a long time, causing database locks.

Don’t ignore exceptions and fail to rollback — this can corrupt data integrity.

Don’t mix multiple DbContexts or database connections without coordinating transactions.

Don’t perform long-running or user-interactive operations inside a transaction.

Don’t use highest isolation levels like Serializable unless absolutely necessary (performance cost).

Don’t nest transactions unless your database explicitly supports it.

Don’t put non-database logic (e.g., calling external services) inside the transaction boundary.

Don’t forget to dispose or close transaction objects properly.

    }

Query Validation Behavior
The QueryValidationBehavior<TRequest, TResponse> is a MediatR pipeline behavior that ensures validation rules are applied to queries before they are handled.

This is part of CQRS (Command Query Responsibility Segregation) where queries and commands are treated differently.

How It Works


public async Task<TResponse> Handle(TRequest request, RequestHandlerDelegate<TResponse> next, ...)
{
  var context = new ValidationContext<TRequest>(request);
}
This wraps your query request (TRequest) in a validation context so validators can access its data.



var validationResults = await Task.WhenAll(
    validators.Select(v => v.ValidateAsync(context, cancellationToken))
);
Runs all registered IValidator<TRequest> implementations asynchronously.



var failures = validationResults
    .Where(r => r.Errors.Any())

    throw new ValidationException(failures);
}
If any validation rule fails, it stops the pipeline and throws a ValidationException.



return await next();
If validation passes, proceeds to the actual query handler to fetch/process data.

Command Validation Behavior
The CommandValidationBehavior<TRequest, TResponse> that you're using is a custom MediatR pipeline behavior designed to validate command requests before they are handled by their respective handlers. This pattern is a clean way to apply cross-cutting concerns such as validation, logging, or authorization. This is located under the BuildingBlocks behaviors.

Purpose
It ensures that commands (requests implementing ICommand<TResponse>) are validated using FluentValidation validators before being executed by their handler.

How It Works


public class CommandValidationBehavior<TRequest, TResponse>
    (IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : ICommand<TResponse>
IPipelineBehavior<TRequest, TResponse>: Part of MediatR, allows you to intercept the handling of requests.

IEnumerable<IValidator<TRequest>> validators: All FluentValidation validators that apply to this specific command (TRequest) are injected.



var context = new ValidationContext<TRequest>(request);
Creates a FluentValidation context using the incoming command.



var validationResults = await Task.WhenAll(validators.Select(v => v.ValidateAsync(context, cancellationToken)));
Runs all applicable validators asynchronously.



var failures = validationResults
    .Where(r => r.Errors.Any())
    .SelectMany(r => r.Errors)
    .ToList();
Collects all validation failures.



if (failures.Any())
    throw new ValidationException(failures);
If any validation errors exist, it throws a FluentValidation.ValidationException. This prevents the command handler from running.



return await next();
If validation passes, the command proceeds to the next behavior or handler.

How It's Registered
In relevant module DependencyInjection.cs file setup:



config.AddOpenBehavior(typeof(CommandValidationBehavior<,>));
This tells MediatR to automatically insert this behavior for any command implementing ICommand<TResponse>, assuming matching validators are registered via:



services.AddValidatorsFromAssembly(Assembly.GetExecutingAssembly());
Example
Suppose you have a command like:



public record CreateStudentCommand(string Email, string Password) : ICommand<Guid>;
And a validator:

{
    public CreateStudentCommandValidator()
    {

        RuleFor(x => x.Password).MinimumLength(6);
    }
}
